Solution Overview

Our solution was based on End-to-end finetuning for LB 0.85 and was also heavily influenced by the following public notebooks. We would like to thank the authors again.

  • Training with Unsloth to Achieve 0.85 LB
  • End-to-end finetuning for LB 0.85

Our approach can be summarized in the following three points.

We made almost no changes to the reasoner (CoT generation logic)

  • The reasoner was based on Open Progress Prize Publication, and we made almost no changes to it.

  • The reasoner could correctly solve 87.8% of the problems, while the best score from the public notebooks was 0.86. Therefore, we believed that if the LLM could reproduce the behavior of the reasoner more faithfully, a high ranking would be achievable.

  • Our approach was not to solve harder problems, but to avoid losing problems that should already be solvable.

  • Below is the final accuracy of our reasoner. It is almost the same as the publicly available one.

We built a new generator and synthesized many similar problems

  • Although the reasoner could correctly solve 87.8% of the problems, the best public notebook score remained at 0.86. We suspected that the gap was caused by a shortage of training data.

  • Therefore, we extracted various task-level statistics from train.csv and built a program that could generate an arbitrary number of rule_found samples.

  • The statistics we used included character frequencies, numeric ranges and distributions, and distributions of transformation methods.

  • To improve the quality of the generator, we trained the model only on synthetic data and evaluated it on both synthetic data and original data. If the synthetic data perfectly imitated the original data, the evaluation accuracy on synthetic data and original data should be the same. By measuring this gap, we identified missing factors in the synthetic data generation algorithm and iteratively fixed them.

  • In the final submission, we trained with a ratio of "synthetic data : original data = 2.5 : 1", using synthetic data first and then original data.

  • Longer training improved the loss, especially on difficult tasks.

Tokenization trick (synthetic tokens for cryptarithm)

  • In cryptarithm tasks, tokenizer segmentation sometimes caused multiple characters to be handled as a single token. This issue was also discussed in the competition discussions.

  • To address this, we used synthetic tokens that force each single character to be encoded as one token, making the learning process more stable.

Additional Improvements

Gradient clipping

  • In the public notebook, the gradient clipping value was set extremely high at 1e9.

  • We found that this was causing training instability, so we clipped gradients at 1.5.

  • There were discussions about scores varying from submission to submission, and we believe this may have been one of the causes.

  • The figure below shows an example where the same training setup produced very different LB scores depending on whether gradient explosion occurred.

Local validation strategy

  • Until the middle of the competition, we validated by training on synthetic data and evaluating on original data. For submissions, we trained on both synthetic data and original data.

  • However, as we improved the quality of the generator, the model became increasingly overfit to the original data, and we observed a divergence between local validation and Public LB.

  • Therefore, for the final stage, we decided to prioritize Public LB, which was based on unseen data, over local validation.

What Did Not Work

Generating CoTs with higher temperature and applying reinforcement learning (SimPO / ORPO)

  • When we inspected model failures, we found that in many cases the model produced CoTs that were very close to the correct ones. Therefore, we thought that instead of only increasing the probability of correct outputs through SFT, we also needed to reduce the probability of failures through reinforcement learning.

  • To create failed examples (rejected), we sampled from the SFT model with temperature set to 1.3.

  • For chosen, we used the output of the reasoner as is.

  • We performed preference learning with SimPO / ORPO using these output pairs. However, it did not improve accuracy as much as expected, so we did not use it in the final submission.

  • In the training logs, we observed some cases where the probability of the chosen side increased, but we saw almost no decrease in the probability of the rejected side, which was what we had expected.

  • We believe that learning did not progress sufficiently because chosen and rejected were too similar.

Solving new problems

  • For us, solving bit_manipulation and cryptarithm tasks and creating CoTs that an LLM could imitate was very difficult.

  • Algorithms that solve these problems with high accuracy require a large amount of search, and it was very difficult for an LLM to imitate them within a limited token budget.

  • We also used Claude Fable 5, but we were not able to develop a sufficiently strong reasoner.
