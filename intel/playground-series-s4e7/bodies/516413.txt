Preliminary work



I started off with my usual baseline routine with a simple EDA and boosted tree models. Considering the size of the data and the potential time and memory constraints to train these models, I restricted myself to Kaggle CPUs and released my EDA component yesterday and trained models locally. I found that XgBoost took lesser time than other options with similar results and decided to work on this model through the day

I was sure that I would not be able to complete too many experiments considering my work schedule and the time to train models with resources at my disposal. Hence, I decided to work on a single model and developed LAMA kernels for the rest. I decided to ensemble them and submit at the end of the day. I released a LAMA kernel yesterday and trained 3 more with different model combinations, with a very similar 5-fold CV score (0.8804 - 0.8809) all on Kaggle CPU

For my private experiments with XgBoost, I compressed the data and released the kernel yesterday. Shrinking the data and using parquet files largely helps in such cases

Key takeaways



My idea of using a single model was perhaps better than trying to build an ensemble. I probably managed my time well to conjure a solution within 6-7 hours of disposable time after work

I should have experimented better with XgBoost parameters. I am sure that using a better value for max bins and n_estimators would have put me in contention for a top 10 finish. Nevertheless, I am happy to be in line with the same line of thought as a topper candidate and shall use these learnings going ahead, perhaps with a better result in times to come. 


Some tips for handling a relatively large dataset



Using Polars lazyframe, PySpark, DataTable and CuDF is better than using pandas with CPU for such datasets. I am using Polars a lot these days and find it much faster than pandas for a lot of commonplace tasks

One may submit using parquet files too. They occupy lesser disk space and take almost the same time to score as a .csv submission

Using one's resources to full use is key. We have 30-hours of Kaggle GPU and up to 5 CPU kernels available at our disposal. Using them to good use is key this month. 

We can hope that we will have a lesser extent of churn this time given the CV-LB relation and the large size of the data

One may avoid CPU intensive work with a GPU, if resources are limited. EDA, data preprocessing, visuals, etc. may be effectuated on a separate kernel with a CPU and GPU based steps may be performed on a GPU kernel to optimize resources. 

One may consider training the model and perhaps predicting on the test set on 2 separate kernels to avoid any potential OOM issues. Also, predicting in batches on the test set is also an option.
