PROBLEM 1: The rewrite prompts for the synthetic dataset can be wonky.

  • When generating your synthetic dataset, the generated rewrite prompts sometimes don't make sense.
  • For Example:
    • "Rewrite this as a brief to be briefed"
    • "Transform this text into a powerpoint presentation"
    • etc
  • It's also hard to know if the rewrite prompts should be short, long, descriptive, etc…

POTENTIAL SOLUTION

  • I wouldn't rely on complete automated rewrite prompt generation.
  • Identify common elements in rewrite prompts and stick with those try to minimize unnecessary variability. The model needs to learn the semantic part AFTER this but it can also learn to - essentially - perform categorical classification on things like the type of text (every little bit helps).
    • Identify common roots (rewrite, rephrase, translate, etc.)
    • Identify common words for text (text, essay, blog post, paragraph, paper, etc.)
    • Identify other commonalities you think could be categorically predicted.
  • As for the generation of these prompts…
    • I would either write them yourself, or generate them with a high quality LLM and then do your best to review as many as possible.
    • Because the synthetic dataset can be a combination of N permutations of original texts with rewrite prompts, the size of the unique rewrite prompt set probably does not have to be that large (1-2 thousand examples with 10-20 thousand rewrite texts would yield ~20-25 Million Examples)

PROBLEM 2: Configuring the model to generate the synthetic datasets rewritten text is hard.\

  • Different implementations of Gemma7B have differences that are sometimes hard to catch.
  • Ideally, you would want to match the hyperparameters used to generate the test set… but we don't know those.

POTENTIAL SOLUTION

  • Use the exact model that the hosts said they used --> gemma-insruct-7b-quant Pytorch model (see the data page).
  • You should also endeavour to use the same prompt templates ([|], [user|model], [end|start]_of_turn, etc.)… this is not always straightforward given that the different implementations handle doing this for you in different ways.
  • Use a greedy sampler.
    • We do this because if you set temperature higher (topk, whatever)… it is still possible to generate the greedy (topk=1 or temperature=0) decoded text…
    • But if we set the sampler to something more non-deterministic, and the hosts themselves used a greedy sampler, we are generating examples that fall outside of the possible distribution…
    • In other words, if we knew which setup to use… we would use that… but it is safer (in my opinion) to use greedy sampling
  • Read up about the implementation you are using and do your best to follow what the paper/google says they did.
  • Likely, the hosts followed the public tutorials on how to generate data (i.e. it's not like a deepmind engineer responsible for the underlying model generated the outputs) and as such if you do your best to follow a similar path you should align with their strategy (hopefully… fingers crossed…)

PROBLEM 3: Your synthetic (generated) rewritten texts are not great… sometimes.

  • If you review some generated examples, you may notice that the model does a bad job rewriting the text. For the sake of simplicity let list some problems:
    • Annoying prefix statement: 'Sure, here is the text rewritten:\n\n', 'The text you requested is shown below:\n\n', etc
    • Missing the point. Sometimes the model just does a bad job rewriting the text. You ask it to do X and for some reason it does Y. I've seen this a lot with more nuanced requests, negative requests (it doesn't like being mean), requests are too generic or specific, or transformation requests that are too difficult.
    • The model will say no. Sometimes the model just refuses to do it and will say so. This can be due to it being impossible/very-difficult/missing-information, but it can also be for other reasons (maybe safety, etc.)
    • The model fails to stop generating. This might just be me, but this definitely happens sometimes.

POTENTIAL SOLUTION

  • OPTION 1: Use an auxiliary model to perform reflection on the generated prompts to remove ones that don't make sense.
  • OPTION 2: Assume the hosts faced similar issues so … just leave them in?
  • OPTION 3: Use rule/pattern based tools to remove/edit/filter the rewritten texts (i.e. remove the prefix statements, get rid of too long/short texts, etc.)
  • OPTION 4: ???

PROBLEM 4: Your collection of synthetic rewrite prompts (and the test site ground truth rewrite prompts) might be impossible or detrimental to try to predict directly.

  • This sounds counterintuitive… but it might not be the best idea to finetune your model using the actual rewrite prompts from your synthetic dataset… yes… those prompts WERE used to generate the rewritten texts… yes… the goal of the competition is to predict that… however, we KNOW we are evaluated within the T5 embedding space and this means we have to understand how that influences our goal.
  • From my exploration of the T5 embedding space, it is clear that more detail (especially irrelevant or incorrect detail) definitely pushes the vector embeddings far away from one another. For example:
    • GROUND TRUTH: "Transform this sentence into a more humorous and sarcastic version, using irony and wit."
    • FULL PREDICTION [Similarity of 0.628] : "Rewrite this text to infuse it with humor and a light-hearted tone, while still conveying the scientific facts and the relative safety due to the distant future impact date."
    • SHORTER PREDICTION [Similarity of 0.715]: "Rewrite this text to infuse it with humor."

POTENTIAL SOLUTION

  • It may make sense to fine-tune the model to output as terse a version as possible to prevent divergence from the original text later in the sentence that might be VERY difficult to avoid.
  • To get a terser representation that maintains the same (or similar but simpler) semantic meaning, we would likely want to use an auxiliary LLM (ChatGPT, Claude, etc.)
  • Therefore we have the following flows:
    1. Original Text + Full Rewrite Prompt --- [GEMMA 7B INFER] ---> Rewritten Text
    2. Full Rewrite Prompt --- [CHATGPT INFER] ---> Condensed Rewrite Prompt
    3. Original Text + Rewritten Text --- [SMALL LLM TRAIN] ---> Condensed Rewrite Prompt
  • The last flow should give us a trained model that outputs a condensed rewrite prompt that ideally is more semantically similar (in the T5 embedding space) than if we had trained it on the full Rewrite Prompt.

PROBLEM 5: The evaluation embedding space is different than the training embedding space.

  • This is related to PROBLEM 4, but still worth acknowledging separately.
  • If you consider the embedding space of your trained model (Gemma or whatever), the predicted text's vector representation may be nearly identical to the ground truth vector representation, however, it may still have a large cosine distance within the T5 (evaluation) embedding space.
  • This happens because the embedding space represents the model's understanding of the semantic meaning (w.r.t. the task it was trained on… probably just language generation) of language, and while you might think that wouldn't diverge that much, model to model, you'd be wrong.
  • In other words, Gemma might think two sentences are similar, huzzah, we did it! But T5 might think they are quite different (oh no…)
