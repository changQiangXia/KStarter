First off, thank you to all the participants and the organizers for this fantastic competition!

I spent a ton of time on code golf for the first time in about 20 years. Back in the day, as a code golf enthusiast, I enjoyed golfing various ICPC problems in C++. This time, I participated as an enthusiast of AI Agents and test-time inference, and I thoroughly enjoyed every moment of it. I found myself endlessly spending time trying to push the boundaries of what AI can do. I'm actually relieved the competition is finally over☺️.

For my contributions, at least, I'd say my solutions were 98% generated by an LLM and only about 2% by human effort. To be honest, I don't even understand most of the final golfed code. Here, I'll describe my part of our team's approach.

Parallel Sampling

My core strategy was to have an LLM (gpt5-codex) perform code golf using tools in parallel. gpt5-codex has very high tool utilization capabilities, and was able to analyze JSON test cases in a REPL and do various things on its own. For each task, we would run a single conversation session consisting of 10-30 turns. This entire process was repeated many times every day. The duration of a single turn varied depending on the problem's difficulty, ranging from 5 minutes to over an hour.

The figure below illustrates one "turn" in a session. It begins with a prompt and generated 4 parallel versions. Then, each generated code is evaluated, and the shortest valid code is selected. Code golfing continues with a follow-up prompt for the next turn.



Rule-based Prompt Generation

Through experimentation, I found that providing the LLM with specific, concrete ideas for improvement was effective. The base follow-up prompt was simple:




On top of this, I generated additional rule-based prompts using the code's AST. For example:



If the code didn't use regular expressions, I added: "Try to use the regex&nbsp;re&nbsp;package to code golf. It might be a key to a breakthrough."

If the code used loops, I instructed it to try converting them into recursive functions.

If a function was defined with&nbsp;def, I prompted it to use&nbsp;lambda. While not always optimal, this was often the better choice.


I co-developed the AST-based prompt generation script with&nbsp;grok4-code-fast-1&nbsp;and&nbsp;gpt5-codex. If I had embedded more domain-specific code golf knowledge into these rules, the speed of improvement could have been even faster.

Codex Cloud (Web)

With the exception of the first two weeks of August, I primarily used Codex Cloud, following the framework described above. In Codex Cloud, you can't explicitly select a model, but I believe gpt5 was used for the first month and gpt5-codex for the latter two. I ran about 15 conversation sessions in parallel, with each turn in every session executing 4 parallel versions (N=4).
All of this was done within the limits of a ChatGPT Pro subscription.

This workflow was essentially a human-in-the-loop algorithm: I manually operated Codex Cloud based on a set of rules. Even when I was away from my PC—on a bus, on a train, or waiting for a flight—I was constantly pasting prompts into my smartphone and hitting submit every single day for three months. It felt like being a worker in a dystopian world.



codex exec (CLI)

The daily work of copying and pasting in Codex Cloud was painful, so I attempted to automate and scale up the process using the&nbsp;codex exec&nbsp;(CLI) and API credits. Due to cost constraints, I haven't run it very often. I ran it while sleeping or during work.

To create a safe environment for code improvement, I set up a Docker container and ran the&nbsp;codex exec&nbsp;(CLI) inside it. The results of these experiments were logged to an SQLite database. Using a managed sandbox environment like&nbsp;katakate&nbsp;might be a better approach.

I also experimented with ensembling different models like Grok4, but I didn't spend enough time for prompt engineering and gave up before getting good results. For example, when I used&nbsp;grok4-code-fast-1&nbsp;with codex, I recall it trying to download ARC testdata with&nbsp;curl, failing to use tools correctly, and taking a roundabout thought process. This could likely have been improved with better prompt tuning.&nbsp;grok4&nbsp;performed relatively well but was burning through my API credits at an alarming rate, so I abandoned it quickly.

Escaping Local Optima

When using Codex Cloud (Web), the model had access to the repository containing the previously generated code. This often caused it to get stuck in a local optimum, unable to break away from the existing solution.

To solve this, when using&nbsp;codex exec&nbsp;(CLI), I created a clean, empty sandbox environment for each new session. This forced the model to start from a blank slate. I remember breaking out of several difficult local optima on a few tasks using this method.

LLM optimize for "compression-friendly" code

In the last 2 weeks, I managed to significantly improve our scores by having the LLM optimize for "compression-friendly" code. The idea was to generate code that would be highly compressible with zip(zopfli).
