Heyho everyone,

The following details our approach during this competition. In addition, we provide supplementary information and an aggregation of our main contributions into one code file via this GitHub repository.



The notebook by @gauravduttakiit really changed this competition because we found nothing in our offline evaluation that explained why this specific model and preprocessing was so good on the public leaderboard. Thus, it seemed like the notebook won a lottery ticket on the public leaderboard. 

An alternative theory was that renaming the columns had some unknown impact that we could not reproduce or pinpoint. We also investigated replacing values with Null (as described here), but this only gave a small increase in offline validation score, which we also got by other means. 

Thus, we opted to include it in an ensemble together with our own submission.  As @roberthatch pointed out, this made the rest of the competition an averaging gamble. 

Although it seems we took a bit of a different approach to produce the average at the time. In detail, we opted to produce a weighted ensemble of the model created by @gauravduttakiit and our own submission. To do so, we took the notebook's data and used FLAML to get prediction probabilities of the winning lottery ticket model (loosely related, see this):

Then, we averaged the prediction probabilities and finally converted the average into the final submission. We used a weight of 0.14 (our submission) and 0.86 (the winning lottery ticket model).

Details on Our Submission

For our own submissions, we used an offline evaluation setup to determine how to configure AutoGluon for a three-hour training run. 

Early Stopping Metric

We started using log loss as an early stopping metric in AutoGluon very early on. Importantly, when doing this with the following code, our evaluation metric (i.e., accuracy) is still the selection metric and used for post hoc ensembling!

After we saw the notebook, which used ROC AUC instead of Log Loss, we also implemented and tested how it would perform. This, however, did not improve performance.   

Overview of Other Offline Evaluation Results

In our offline evaluation, we also came to the following conclusions:



Treating ordinal features as numerical features is beneficial.

Using original data is better for model performance (even with its distribution shift).

Using sample weights does not help.

Using repeated cross-validation is beneficial. 

Using transductive learning is beneficial. Yet, we did not use it in our submissions as we did not trust the results of our test. 

We verified that gradient-bosted decision trees (GBDTs) and neural networks (NNs) are both capable of solving this task. 


Stacking

We noticed that NNs were much better than GBDTs among all stacking models. Based on our prior work on stacked overfitting, we knew this pattern and thus opted not to use GBDTs as stacking models anymore, which further improved offline performance.

Feature Engineering

We used OpenFE to obtain new features, which improved our offline validation score. We do not know if it made our final submission worse, as the lottery ticket model did not use similar features. 

EDA

We looked at the features with EDA, but nothing seemed off nor worthy of further manual investigation.
