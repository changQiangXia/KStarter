### Subjective Competition Learnings (or a list of problems I encountered and possible solutions)

来源：https://www.kaggle.com/competitions/llm-prompt-recovery/discussion/483916

Hi all, here we go:

PROBLEM 1: The rewrite prompts for the synthetic dataset can be wonky.

When generating your synthetic dataset, the generated rewrite prompts sometimes don't make sense.

For Example:

"Rewrite this as a brief to be briefed"

"Transform this text into a powerpoint presentation"

etc

It's also hard to know if the rewrite prompts should be short, long, descriptive, etc…

POTENTIAL SOLUTION

I wouldn't rely on complete automated rewrite prompt generation.

Identify common elements in rewrite prompts and stick with those try to minimize unnecessary variability. The model needs to learn the semantic part AFTER this but it can also learn to - essentially - perform categorical classification on things like the type of text (every little bit helps).

Identify common roots (rewrite, rephrase, translate, etc.)

Identify common words for text (text, essay, blog post, paragraph, paper, etc.)

Identify other commonalities you think could be categorically predicted.

As for the generation of these prompts… 

I would either write them yourself, or generate them with a high quality LLM and then do your best to review as many as possible.

Because the synthetic dataset can be a combination of N permutations of original texts with rewrite prompts, the size of the unique rewrite prompt set probably does not have to be that large (1-2 thousand examples with 10-20 thousand rewrite texts would yield ~20-25 Million Examples) 

PROBLEM 2: Configuring the model to generate the synthetic datasets rewritten text is hard.\

Different implementations of Gemma7B have differences that are sometimes hard to catch.

Ideally, you would want to match the hyperparameters used to generate the test set… but we don't know those.

POTENTIAL SOLUTION

Use the exact model that the hosts said they used --> gemma-insruct-7b-quant Pytorch model (see the data page).

You should also endeavour to use the same prompt templates ([|], [user|model], [end|start]_of_turn, etc.)… this is not always straightforward given that the different implementations handle doing this for you in different ways.

Use a greedy sampler.

We do this because if you set temperature higher (topk, whatever)… it is still possible to generate the greedy (topk=1 or temperature=0) decoded text…

But if we set the sampler to something more non-deterministic, and the hosts themselves used a greedy sampler, we are generating examples that fall outside of the possible distribution…

In other words, if we knew which setup to use… we would use that… but it is safer (in my opinion) to use greedy sampling

Read up about the implementation you are using and do your best to follow what the paper/google says they did. 

Likely, the hosts followed the public tutorials on how to generate data (i.e. it's not like a deepmind engineer responsible for the underlying model generated the outputs) and as such if you do your best to follow a similar path you should align with their strategy (hopefully… fingers crossed…)

PROBLEM 3: Your synthetic (generated) rewritten texts are not great… sometimes.

If you review some generated examples, you may notice that the model does a bad job rewriting the text. For the sake of simplicity let list some problems:

Annoying prefix statement: 'Sure, here is the text rewritten:\n\n', 'The text you requested is shown below:\n\n', etc

Missing the point. Sometimes the model just does a bad job rewriting the text. You ask it to do X and for some reason it does Y. I've seen this a lot with more nuanced requests, negative requests (it doesn't like being mean), requests are too generic or specific, or transformation requests that are too difficult.

The model will say no. Sometimes the model just refuses to do it and will say so. This can be due to it being impossible/very-difficult/missing-information, but it can also be for other reasons (maybe safety, etc.)

The model fails to stop generating. This might just be me, but this definitely happens sometimes.

POTENTIAL SOLUTION

OPTION 1: Use an auxiliary model to perform reflection on the generated prompts to remove ones that don't make sense.

OPTION 2: Assume the hosts faced similar issues so … just leave them in?

OPTION 3: Use rule/pattern based tools to remove/edit/filter the rewritten texts (i.e. remove the prefix statements, get rid of too long/short texts, etc.)

OPTION 4: ???

PROBLEM 4: Your collection of synthetic rewrite prompts (and the test site ground truth rewrite prompts) might be impossible or detrimental to try to predict directly.

This sounds counterintuitive… but it might not be the best idea to finetune your model using the actual rewrite prompts from your synthetic dataset… yes… those prompts WERE used to generate the rewritten texts… yes… the goal of the competition is to predict that… however, we KNOW we are evaluated within the T5 embedding space and this means we have to understand how that influences our goal.

From my exploration of the T5 embedding space, it is clear that more detail (especially irrelevant or incorrect detail) definitely pushes the vector embeddings far away from one another. For example:

GROUND TRUTH: "Transform this sentence into a more humorous and sarcastic version, using irony and wit."

FULL PREDICTION [Similarity of 0.628] : "Rewrite this text to infuse it with humor and a light-hearted tone, while still conveying the scientific facts and the relative safety due to the distant future impact date."

SHORTER PREDICTION [Similarity of 0.715]: "Rewrite this text to infuse it with humor."

POTENTIAL SOLUTION

It may make sense to fine-tune the model to output as terse a version as possible to prevent divergence from the original text later in the sentence that might be VERY difficult to avoid.

To get a terser representation that maintains the same (or similar but simpler) semantic meaning, we would likely want to use an auxiliary LLM (ChatGPT, Claude, etc.)

Therefore we have the following flows:

Original Text + Full Rewrite Prompt --- [GEMMA 7B INFER] ---> Rewritten Text

Full Rewrite Prompt --- [CHATGPT INFER] ---> Condensed Rewrite Prompt

Original Text + Rewritten Text --- [SMALL LLM TRAIN] ---> Condensed Rewrite Prompt

The last flow should give us a trained model that outputs a condensed rewrite prompt that ideally is more semantically similar (in the T5 embedding space) than if we had trained it on the full Rewrite Prompt.

PROBLEM 5: The evaluation embedding space is different than the training embedding space.

This is related to PROBLEM 4, but still worth acknowledging separately.

If you consider the embedding space of your trained model (Gemma or whatever), the predicted text's vector representation may be nearly identical to the ground truth vector representation, however, it may still have a large cosine distance within the T5 (evaluation) embedding space.

### 2nd place solution: Team Danube

来源：https://www.kaggle.com/competitions/llm-prompt-recovery/discussion/494497

Thanks for hosting this competition, we had fun trying to optimize for the given t5 metric and incorporating some useful modeling approaches to our solution. As always, great teamwork with @ilu000 and @ybabakhin.

Here we want to highlight the main chronological steps to come up with our solution and relevant thought processes.

Mean prompts and bruteforce optimization

When we joined together in the competition, mean prompts dominated the public and our individual solutions and seemed the most low hanging fruit going forward, specifically also after we figured out that t5 metric is very sensitive and just raw llm predictions will not be too useful. So we decided to keep exploring optimal mean prompts.

We quickly saw that just manually trying things is not effective, so we started exploring how to brute force the actual tokens for optimal mean prompts. We took our training datasets, and tried to brute force each of the ~32k possible t5 tokens to form the most optimal mean prompt for the average of the target vectors. But after submitting that, we got bad results leaving us initially puzzled. Obviously, </s> is an important token in the optimization given that it is appended to each of the target vectors. After exploring this further, we found out that tensorflow is using the original SentencePiece tokenizer, which has protection against special token injection, and thus does not directly tokenize the string </s> as the correct eos token. 

Given this insight, we excluded special tokens in the brute force optimization, and, as many others, the optimizer now really started to like tokens like lucrarea being close to eos token in embedding space. This allowed us to get much closer LB scores compared to our CV scores and we managed to get to around 0.65 with just optimizing the mean prompt that way.

Embedding models

However, we still wanted to directly find a model that can do parts of this job. Specifically, we tried to directly train a model predicting the expected embedding. A simple way of doing that, was to train a classification model in H2O LLM Studio, where we use the 768 output embedding dimensions as the target in our training data. We then also directly implemented a cosine similarity loss, so that the model would directly learn our target metric. With this approach, we managed to get to local scores of around 0.75+ with our embedding predictions. Our embedding models either used H2O-Danube / H2O-Danube2 models, or Mistral 7b with little difference only.

However, the main issue still was that we need to go back from predicted embeddings, to the string representations that are then used in the metric for calculating the t5 sim. We thought of directly modeling this as well in some way, but then resorted back to the bruteforce optimization routine that greedily tries token combinations to match the predicted embedding as closely as possible. Within a certain runtime, we managed to lose around 3-4pts with this optimization, so getting to local scores of around 0.71 and LB scores of around 0.68 or 0.69 just bruteforcing each individual embedding prediction.

LLM predictions and improvements

This was bringing us into the gold zone. Now we tried to find ways of closing the gap between the bruteforce and predicted embeddings a bit further. The first thing we found, that it is actually helpful to initialize the optimization with raw llm predictions, but only predicting the actual change needed to make, such as “as a shanty”. So we prepared our data in that way, and trained llms and incorporated them into our solution as a starting point for the optimization, and also adding them to the embedding blend. Furthermore, for diversity, we also added few shot predictions to that mix. And to even further improve the quality and speed of the optimization, we also added a good working mean prompt there.

This means that our final starting point for the optimization is:

Few shot predictions + LLM predictions + Mean prompt

And the final predicted string is:

Few shot predictions + LLM predictions + Mean prompt + Optimized embedding string (20 tokens)

Data and CV

For all the parts described above, we generated various kinds of data for training and optimization. We also crafted a validation set of ~350 samples where we saw good correlation between local mean prompt scores and submitted mean prompt scores and developed our solution on that. ### 1st place solution: adversarial attack

来源：https://www.kaggle.com/competitions/llm-prompt-recovery/discussion/494343

Inference notebook: https://www.kaggle.com/code/suicaokhoailang/1st-place-0-71

TL;DR: Append this string to your model prediction and see score going up for up to +0.05: 

 
" 'it 's ' something Think A Human Plucrarealucrarealucrarealucrarealucrarealucrarealucrarealucrarea"

For example:

 
Convert this to a shanty. 'it 's ' something Think A Human Plucrarealucrarealucrarealucrarealucrarealucrarealucrarealucrarea"

My explanations (or what I've known so far):

It's not about lucrarea, but the </s> token. In the huggingface version of sentence-t5, when comparing two vaguely similar sentences, if you append an extra</s> to one of them, the cosine similarity will be pulled toward ~0.9 i.e. if the original is lower, it goes up, if higher it goes down. 

0.9 translates to about 0.73 of competition metric, now you're seeing where this is going.

However, the tensorflow version, which the host used to compute the score, uses the default config of sentencepiece, which means it will tokenize special tokens as literal, </s> becomes ['<', '/', 's', '>']

Here comes lucrarea, by computing the embeddings of all tokens in the t5 vocab, you'll find some which are extremely close to </s>, lucrarea included. 

Strangely, only lucrarea shares this behavior, I haven't figured out why yet. Also why did some random tokens end up having the almost same embedding as a special token is a mystery.

lucrarea is basically a Walmart version of </s>, only pull scores to 0.71, thanks Data Jesus that's enough to win. 

It's understandable that messing with special tokens leads to unexpected behavior, but it leading to such a high score may just be pure luck for me.

My theory

I think the special token pulls a sentence to some focal point in the embedding space, maybe the center of it.

If the sentence are far enough from each other, it's more likely that the new distance (green) is shorter than the old one (orange). But if the two sentences are already very close to each other, this can hurt performance.
