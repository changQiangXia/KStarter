## write-up 正文（8 篇）

### 1st Place Solution

来源：https://www.kaggle.com/competitions/nvidia-nemotron-model-reasoning-challenge/discussion/709231

Acknowledgements

First, we would like to thank NVIDIA and Kaggle for hosting such an interesting competition. We also thank the participants who shared useful ideas through public notebooks and discussions during the competition. We were very happy to finish 1st on both Public LB and Private LB. This was the first Kaggle gold medal for all members of our team. In particular, we learned a lot about trace design and training strategy across multiple task categories from the Open Progress Prize Publication by @huikang. Also, Strategy to solve 85% of bit manipulation by @huikang was the direct starting point for our bit manipulation solver.

Summary

The core of our solution was deciding what the model should memorize through synthetic traces and what it should compute inside the trace.

The overall pipeline was simple: generate synthetic problems, attach solver-generated traces, and train the model with SFT.

For cryptarithm, we precomputed candidate digit assignments from a single equation and made the model memorize them. Memorization alone does not determine consistency across multiple equations, so we checked that part sequentially with DFS.

For bit manipulation, we started from the solver by @huikang. We compressed long bit strings into HEX to free token budget, and then repaired the selected 8-rule sequence by checking nearby valid sequences from a precomputed rule-sequence catalog.

Competition Overview

The NVIDIA Nemotron Model Reasoning Challenge was a competition to improve the reasoning ability of Nemotron-3-Nano-30B. Each prompt gives several input-output examples. The task is to infer the hidden transformation and apply it to the final query. The provided train.csv contained 9,500 labeled problems across bit manipulation, equation numeric, cryptarithm, text cipher, numeral system, unit conversion, and gravity.

Submissions were restricted to LoRA adapters for Nemotron-3-Nano-30B, with LoRA rank <= 32. At evaluation time, the submitted adapter was loaded with vLLM, and accuracy was computed by checking whether the final answer inside \boxed{} matched the ground truth. String answers required exact match, while numeric answers allowed relative error 1e-2. The generation settings were temperature=0.0, top_p=1.0, and max_tokens=7680, so the model had to produce the reasoning trace and final answer within that token budget.

This setup meant that we could not run a program at evaluation time to compute the answer.

Trace Design

After reading the Open Progress Prize solution by @huikang, we concluded that the main room for improvement was in cryptarithm and bit manipulation. Many submissions were around 0.86 on the Public LB, and the number of submissions around 0.87, which looked like strong improvements over the solution by @huikang, was also increasing. Because evaluation scores had variance, we needed a clear gap in these two categories rather than staying in a range where randomness could decide the final ranking.

Equation Numeric

Task Format

In Alice's Wonderland, a secret set of transformation rules is applied to equations. Below are a few examples:
55`39 = 16
61\65 = 126
42>23 = 4223
17\21 = 38
Now, determine the result for: 81`20

In equation numeric, two 2-digit numbers are transformed by an operator defined inside the prompt. Each line has the form 2 digits + operator + 2 digits = output. The important point is not to read symbols such as `, \, and > by their visual meaning. The meaning of each operator changes from prompt to prompt. In the final query, we apply the operator meaning inferred from the same prompt. Sometimes the query operator does not appear in the examples, so there is no direct input-output example for that operator.

In this example, 55`39 = 16 tells us that ` means 55 - 39. The examples 61\65 = 126 and 17\21 = 38 tell us that \ means addition. The example 42>23 = 4223 tells us that > concatenates the two 2-digit inputs. Therefore, the query 81`20 becomes 81 - 20 = 61, and the answer is \boxed{61}.

Solution

In the trace, we first parse each equation as AB op CD = output and collect examples for each operator. Then, for each operator, we check which rules in the 24-rule inventory reproduce its examples. When multiple rules remain, we use prompt-level mode and group constraints, plus operator priors for +, -, and *, to narrow them down. Once the operator rule for the query is fixed, we apply that rule to the 2-digit query inputs. By analyzing equation numeric in train.csv, we found that all operator transformations could be explained by the same 24-rule inventory. Two observations were especially important.

Observation 1: In one prompt, all non-join operators use the same mode. If one operator is explained by a normal mode rule, then the other non-join operators in the same prompt are also explained by normal mode rules. Conversely, in a flip mode prompt, all non-join operators use flip mode.

Observation 2: In one prompt, non-join operators do not reuse the same group. For example, if one operator uses the add group, another non-join operator uses the sub or mul group. The join group is an exception and can appear independently of the normal / flip mode choice.

Cryptarithm

Task Format

In Alice's Wonderland, a secret set of transformation rules is applied to equations. Below are a few examples:
|!)<< = <[[
::$\{ = !{?
<<$'' = {\|(
Now, determine the result for: !')?<

Cryptarithm is an equation task where digits are hidden by symbols. The left side of each equation has 5 characters: 2 symbols + operator + 2 symbols, so it has the form AB op CD = output. In the first line, |!)<< = <[[, the operator is ) between |! and <<, and the output is <[[. After mapping symbols back to digits, this becomes a 2-digit op 2-digit = 3-digit equation. In this category, we must determine both the digit assignment and the operator rule assignment. The query also has the same 2 symbols + operator + 2 symbols form, and the computed numeric result must be mapped back to symbols. Sometimes the query operator does not appear in the examples, so both the digit assignment and the query operator rule must be inferred without a direct example for that operator. In this example, the answer is \boxed{:![}. The final assignment is:

Solution

For cryptarithm traces, we used the same 24-rule inventory from equation numeric as candidates for operator rules. Observation 1, the mode constraint, and Observation 2, the group constraint, were also consistent with cryptarithm, so we used them for DFS pruning. On the other hand, the operator priors for +, -, and * did not transfer well enough, so we did not use them.

The naive search space is too large to write out as a teacher trace. In train.csv cryptarithm prompts, up to 10 digit symbols and up to 3 operator symbols appear. A rough upper bound for full search is:

digit assignments: 10! = 3,628,800
operator rules: 24^3 = 13,824
total combinations: about 5e10 candidates

This cannot be reproduced token by token within the 7680 generation-token budget. Therefore, the problem was not only to solve the task, but also to decompose the search into a short procedure that the model could follow inside a trace.

The first check is join / join_swap. We inspect all equations and see whether the output is simply the two inputs concatenated. If an equation matches, the rule assignment for that operator is determined immediately.

join: AB op CD -> ABCD
join_swap: AB op CD -> CDAB

For example, in a symbolic prompt, if we see !>*}> = !>}>, then operator * can be identified as concatenating the two inputs !> and }>. If the same operator appears in the query, we can answer by concatenating the two query inputs. These two rules recover about 5% of cryptarithm problems. The Open Progress Prize solution by @huikang reached this stage for cryptarithm.

Many cryptarithm problems remain after join / join_swap, so we solve the rest with DFS. First, choose one equation and list candidates for the rule and digit assignments that satisfy that equation. After choosing one candidate, check the remaining equations in order: the same symbol must map to the same digit, and the same operator must map to the same rule. If a contradiction appears, move to the next candidate. Once an assignment consistent with all equations is found, decode the query. When generating candidates for a single equation, we also used filters based on modular arithmetic and inequalities. However, it was difficult to pack that candidate-generation process into a short trace, and that alone did not produce a large score gain.

The breakthrough was the signature viewpoint. A signature represents where the same symbols repeat and where the sign marker appears on the output side. For example, in '^-"} = -@@, the left operand '^ corresponds to AB, the right operand "} to CD, and the answer -@@ to signed EE, so the signature is ABCD-EE. The signature viewpoint and the precomputed operation-table approach were discussed in A Pattern-Matching Approach to Solving Symbolic Arithmetic Puzzles by @youkinasa. That discussion described using a precomputed operation table keyed by signature to reduce solver candidates, instead of directly running brute force search. Our addition was to turn this into a signature catalog that the model memorizes through repeated SFT traces, rather than using it as a program at inference time. Since we cannot execute a program at evaluation time in this competition, it was important for the model to recall candidate counts and candidate digit assignments from the signature.

This fit the hard part of DFS very well. The expensive step in DFS is the first equation. In the first equation, the solver typically has to assign about 4 to 8 digit symbols and the rule for that equation at once. In later equations, the digits fixed by the first equation can already be used, so the number of newly assigned symbols is often only about 0 to 3. Therefore, we precomputed one-equation candidates for each signature and trained the model to memorize this signature catalog. Instead of discovering candidates for the first equation from scratch every time, DFS starts from candidates retrieved from the catalog and only checks consistency with the remaining equations.

The signature catalog was built by exhaustively enumerating the two 2-digit operands on the left side of an equation. Concretely, we assigned 00..99 to the left operand and 00..99 to the right operand, applied each of the 22 non-join rules, and computed the output. Then we normalized the digit sequence left operand + right operand + output by first occurrence into A,B,C,.... This sequence is the signature. This enumeration produced 4205 unique signatures. The signature catalog includes signatures such as AAAAA, ABCCCDD, AABBCDEF, and ABCD-AE. Each signature maps to candidate rows, each consisting of an operator rule, a slot digit string, and a candidate count. For example, ABCCCDD has:

Bit Manipulation

Task Format

In bit manipulation, the prompt gives several input -> output examples, and we need to find the common 8-bit transformation and apply it to the final query. The left side is an 8-bit binary input, and the right side is an 8-bit binary output. All examples in one prompt are generated by the same transformation.

In Alice's Wonderland, a secret bit manipulation rule transforms 8-bit binary numbers. The transformation involves operations like bit shifts, rotations, XOR, AND, OR, NOT, and possibly majority or choice functions.

Here are some examples of input -> output:
00010101 -> 10000011
01100011 -> 10111001
11000101 -> 01111000
00011010 -> 10100011
01010110 -> 00000011
11010001 -> 00011010
10100010 -> 00110110
00111111 -> 01111011
11000011 -> 01111100
01110101 -> 11001111

Now, determine the output for: 01101001

One transformation that fits this example is:

s = not(rol1(x))
a = not(shr3(x))
b = shl2(x)
out = sel_nand_xnor(s, a, b)

Here, sel_nand_xnor(s, a, b) uses nand(a,b) where each bit of s is 1, and xnor(a,b) where each bit of s is 0. Applying it to the query gives:

x = 01101001
s = not(rol1(x)) = 00101101
a = not(shr3(x)) = 11110010
b = shl2(x) = 10100100
out = 10001101

Therefore, the final answer is \boxed{10001101}.

Solution

The solution by @huikang does not try to guess all 8 output bits at once. Instead, it searches for an expression for each output bit in terms of input bits. For example, for output bit 0, it may try using input bit 0 directly, negating input bit 1, or taking AND / OR / XOR of two input bits. If an expression reproduces output bit 0 for all examples, it becomes the rule for output bit 0. However, the solver does not simply choose each bit rule independently. It first tries input bits, negations, constants, and two-bit AND / OR / XOR rules, and builds a table of which output bit each expression can reproduce. Then it searches from the left for sequences where input references advance one by one, such as AND57, AND60, AND71. It also searches from the right and prefers longer consecutive sequences. If middle bits remain unresolved, it checks whether they can be filled by constants or similar operations using input positions predicted by the left and right sequences. Finally, it applies the selected 8-rule sequence to the query. This "find per-output-bit rules, then choose consistent left and right sequences" idea was very strong and became the starting point of our bit manipulation solution.

We made three main improvements to this starting point.

Convert long bit-column sections of the trace to HEX to reduce token count.

Add rules that the original solution did not cover, such as majority, 3-input parity, conditional selection, and 3-input compositions.

Instead of using the selected sequence as-is, repair it by checking nearby valid 8-rule sequences from a precomputed rule-sequence catalog.

For the additional bit rules, we first collected candidate rule families from existing discussions, public notebooks, and our analysis of train.csv. We then adjusted the rule set by adding and removing rule families while keeping the ability to explain all bit manipulation examples and queries in train.csv. This gave us a compact rule set for the rule-sequence catalog instead of an unnecessarily broad enumeration.

The biggest limitation of the solution by @huikang was token count. The original traces repeat bit columns many times. Also, unlike many other tokenizers, Nemotron's tokenizer behaves close to one token per digit or bit character. Therefore, replacing long binary strings with hexadecimal strings directly reduces output tokens. We converted bit strings of length 4 or more to HEX. With the same sample set and training code, the median number of generated tokens decreased from 6771 to 4888 (27.8% reduction). Early HEX traces lowered accuracy, but increasing synthetic data with HEX traces recovered much of it while keeping the shorter output length.

Even if each output bit rule matches the examples locally, the 8 rules as a sequence are not necessarily possible as one coherent 8-bit transformation. In particular, the baseline procedure can produce fallbacks such as default 1. This means "we failed to find a good rule for this bit, so fill it with a constant", and such a sequence does not exist in the rule-sequence catalog. Therefore, we enumerated theoretically possible 8-bit transformations from the list above and converted each into per-output-bit operation notation. Concretely, each 8-bit transformation is normalized into an 8-rule sequence: "rule for output bit 0, rule for output bit 1, …, rule for output bit 7". For example, sel_nand_xnor(not(rol1(x)), not(shr3(x)), shl2(x)) becomes XNOR12 XNOR23 XNOR34 SEL-NAND-XNOR045 SEL-NAND-XNOR156 SEL-NAND-XNOR267 OR-NOT73 OR-NOT04. As another example, maj(rol2(x), shl4(x), shr7(x)) becomes AND24 AND35 AND46 AND57 C0 C0 C0 AND01. After removing duplicates, this precomputation produced 5238 valid 8-rule sequences.

Repair means replacing the selected sequence from the baseline procedure with a nearby valid sequence from the rule-sequence catalog. We used Hamming distance as the distance metric. We can view this as a nearest-neighbor projection onto the valid rule-sequence catalog under Hamming distance. Even when the baseline procedure produces default or a local mistake, checking nearby valid sequences can restore a coherent 8-bit transformation. This is the same memorization-computation split as in cryptarithm. The model internalizes the rule-sequence catalog, and then checks within the trace whether each catalog candidate matches the examples. Instead of expanding the full catalog, the trace only checks catalog candidates near the selected sequence, keeping the amount of verification small while still using memorized structure.

The idea of training the model on this repair came from the success of memorizing the signature catalog and candidate counts in cryptarithm. For bit manipulation, we decided that it was not enough to simply apply the selected sequence from the baseline procedure. It was more effective to make the model memorize nearby valid sequences and verify them against the examples to repair the final answer. The trigger for trying this format was an accidental inconsistent trace during development. In a bit problem where the local solver output differed from the ground truth, we accidentally created a training sample where the trace up to the end came from the solver, but the final \boxed{} was replaced with the ground-truth answer. This was not a proper trace imitation target, but the model learned the format. In fact, we saw cases where the solver would be wrong, but the trained model changed only the final answer and became correct.

Even before adding this repair, we reached Public LB 0.89. With repair and extra training, the final system reached Public LB 0.91 / Private LB 0.920. The best unselected submission scored 0.932 on Private LB.

Text Cipher

Task Format

In Alice's Wonderland, secret encryption rules are used on text. Here are some examples:
hmxad apdhvdq vid ohexahm apwqvhm -> alice creates the magical crystal
zxuhpl zhvaidq xyqxld txmmhed -> wizard watches inside village
nfddy xohexydq xy ehpldy -> queen imagines in garden
osfqd qddq lssp -> mouse sees door
vid amdtdp zxuhpl dgjmspdq -> the clever wizard explores
Now, decrypt the following text: bxye aihqdq ahqvmd

Text cipher is a word-aligned substitution cipher. The left side is ciphertext, the right side is plaintext, and the query ciphertext must be decrypted using the same mapping. The example sides have the same number of words in the same order, so from hmxad -> alice we can collect character mappings such as h->a, m->l, x->i, a->c, and d->e. This mapping is consistent within one prompt.

In this example, the query word aihqdq becomes chases from a->c, i->h, h->a, q->s, d->e, q->s. Similarly, ahqvmd becomes castle. On the other hand, bxye can only be read as ?ing from the example-derived mapping, because b is unknown. Using the candidate vocabulary and context, we choose king and add b->k. The full decrypted phrase is king chases castle, so the answer is \boxed{king chases castle}.

Solution

The trace directly implements this simple reading. It aligns example sentences word by word, builds a character mapping table, and decodes the query from left to right. If a ciphertext word itself appears in the examples, the trace uses direct word correspondence. Otherwise, it applies the character mapping. When unknown characters remain, it chooses from a candidate vocabulary using word length, repeated-character pattern, and consistency with already fixed characters. The vocabulary is not arbitrary English words. We built it from the 77 words that appear on the plaintext side of text cipher problems in train.csv. This is a strong constraint: for example, instead of searching for ?ing among all English words, the trace only needs to check words in this 77-word vocabulary. This was not our main improvement target, and the procedure was almost the same as the Open Progress Prize text cipher solution by @huikang.

The trace writes down this reading directly. It computes output / input for each example, confirms that the coefficient is consistent, applies the same coefficient to the query, and rounds to two decimal places. We used the Open Progress Prize procedure by @huikang as-is for this category.

Gravity

Task Format

Gravity asks for the falling distance from time t. The prompt explicitly gives d = 0.5*g*t^2, but g changes from prompt to prompt. From the examples, we can compute g = 2*d/t^2: 2*14.92/1.37^2 = 15.8986, 2*144.96/4.27^2 = 15.9009, and 2*85.54/3.28^2 = 15.9020, so g is about 15.90. Solution

The trace writes down this procedure directly. It computes g = 2*d/t^2 from each example, confirms that the values are close, and applies d = 0.5*g*t^2 to the query time. We also used the Open Progress Prize procedure by @huikang as-is for this category.

The trace builds the mapping that decrypts the letters by looping through the examples, then applies it to the query. The model then guesses the phrase and the sentence template using the 77-word vocabulary and the 4 sentence templates.

What follows is an error-correction loop. Equation transform / numeric

Data generation process

Each problem fixes one domain, normal or reversed, shared by every example, and assigns each of its (typically three) distinct operators a single base arithmetic family — subtraction, addition, multiplication, or concatenation. The base relation is perturbed within its family (+/-1 for addition and multiplication; absolute value and negation for subtraction; modulo, written max%min, lives inside the subtraction family) and the chosen domain is applied. The 11 arithmetic rules each appear in a normal and a reversed form (22), and the 2 concatenation rules are domain-independent, for a total of 24 rules. Across the 732 problems, the normal domain accounts for 286 (39.1%) and the reversed domain for the other 446 (60.9%).

Two other notes:

For subtraction, a negative result is marked with the operator character before the digits (opN) or after (Nop), fixed per problem. The placement gates the signed rule: a prefix marker excludes b-a and a suffix marker excludes a-b, pruning the wrong-direction subtraction.

Concatenation does not carry the domain. It is its own family with two orderings, cat(a,b) → abcd and cat(b,a) → cdab, chosen independently per operator. A concatenation operator looks the same whether the problem is normal or reversed, so it never reveals the domain and takes no part in the normal-vs-reversed decision.

Procedure

Each distinct operator can be one of 24 rules to start. We iterate through the examples in the problem. The examples eliminate rules that fail to reproduce the output exactly as a string — leading zeros and sign placement included. After this per-example pass, an operator that appears in the examples is typically down to 1-3 candidates.

Attention then turns to the query operator. If it has not been seen, it starts with all 24 rules. We then narrow the candidate rules for the query operator based on five filtering steps:

Normal vs. reversed from rules. If there is at least one example operator with only normal or reversed rules remaining, this pins the query operator's domain. Concatenation operators abstain.

Normal vs. reversed from zeros in the query. A leading zero in the query's own operands (e.g. 08) pins the reversed domain, and a trailing zero (e.g. 50) pins the normal domain.

Base arithmetic family based on the other symbols. No two operators share the same base relation (subtraction, addition, multiplication). Let the other operators claim their family; assign the query operator to the bucket that is left. If multiple buckets remain, the priority is subtraction, addition, and multiplication. Note that I expected at most three distinct operation symbols in a problem.

a-b vs b-a for subtraction. The position of the negative-sign marker encodes a-b versus b-a, pruning the wrong-direction subtraction rule.

Base family based on query glyph. If the query glyph is a literal +, -, or *, survivors are restricted to that family. This rule comes from the observation that +, -, or * are most frequent and normally represent addition, subtraction, or multiplication, respectively.

Whatever survives is committed in a fixed priority order — by domain (normal before reversed, concatenation last), and within a domain by family (subtraction, then addition, then multiplication, each taking the canonical rule before its +/-1 or sign variants) — so the procedure always emits a single best guess rather than abstaining.

An atom is live at a bit when it reads a real input bit, and dead (zero-filled, shown blank) when its shift has run off the end: SHLa is dead past bit 7−a, SHRc before bit c, while ROTb is always live since it wraps. The output thus breaks into contiguous regions. For every family, there are at most 3 regions in the signatures. In general, the number of regions equals the rule's order (here both 3).

For example, Maj(SHL3, SHR2, ROT1) has three regions resolving as:

Left (bits 0–1): SHR2 is dead (zero-filled), so Maj(SHL3, 0, ROT1) = AND(SHL3, ROT1) — a 2nd-order AND, written AND13.

Middle (bits 2–4): all three atoms are live, so the full 3-input Maj(SHL3, SHR2, ROT1), written Majority316 (the 6 is from 8-c=8-2=6 since a right shift by c equals a left rotation by 8-c over the non-zero portion).

Right (bits 5–7): SHL3 is dead, so Maj(0, SHR2, ROT1) = AND(SHR2, ROT1) — again a 2nd-order AND, written AND61.

It's possible that the number of regions for a rule is less than its order. For example, consider Maj(SHLa, SHRc, ROTb) with a = b. For bits 0 through 7-a, SHLa equals ROTa, and since Maj(ROTa, SHRc, ROTa) = ROTa, those bits are the input rotated left by a (which I denote as Ia). Bits 8-a to 7 are Maj(0, SHRc, ROTb), which equals the AND between the input shifted right by c and the input rotated left by b (which I denote as ANDb{8-c}, again since a right shift by c equals a left rotation by 8-c over the non-zero portion). Hence, this Maj rule leaves a two-region signature.

Importantly, under the data-generation hypothesis, a, b, and c range from 1 to 7. Because every shift is at least 1, SHRc is dead at bit 0 and SHLa is dead at bit 7, so both left and right regions have at most two live atoms (the always-live ROTb plus either shift). Therefore, for every rule in the grammar, the left and right regions (for no-op, these overlap on all 8 bits) are at most 2nd-order functions of the input:

0th-order (LOW, HIGH): the output bit is a constant 0 or 1, reading no input bit.

1st-order (Identity, NOT): the output bit is a single (rotated) input bit, as-is or complemented.

2nd-order (AND, OR, XOR, ANDNOT, ORNOT, XORNOT): the output bit is a boolean function of two (rotated) input bits.

This fact justifies why we only need to consider these 10 functions for the corner regions (the left region that includes bit 0 or the right region that includes bit 7). Further, the corner regions can narrow down the operator pattern for the middle region and determine how long the regions should be: this means we can enumerate left/right region pairs, filter for pairs that fit the signature, and use the left/right pairings to determine the signature. "Final summary E" of this MD file includes a comprehensive list of signatures. The middle region is one of three forms — LOW, NOT, or an "unknown" function. Only the unknown case needs a brute-force check.

Over-run. We may have a spurious match longer than the true match in a op family. We search the runs within the families until the first hit with length error 0 (e.g. ID 649bebaf).

Shape C. If no shorter corner fits, take the longest XORNOT/ORNOT pair and evaluate Shape C, ((SHLa XOR ¬ROTb) OR SHRc) AND ¬(SHLa AND ROTb AND SHRc) (e.g. ID 05b5ffe1).

Overall, this solution:

Keeps in mind the 7680-token budget: employs hex-binary, avoids double computation for commutative binary ops, enumerates two-region and three-region with middle LOW or middle NOT only when necessary, and minimizes per-bit brute-force verification by stopping at the first full match.

Reduces spurious matches by considering nonzero-shift operators only and matching based on signatures.

Uses shift logic to determine the middle bits and true region lengths.

Equation transform / symbol

I largely left this category alone. For $n$ distinct digits, a brute-force solver would have to enumerate $n!$ symbol-to-digit mappings. Assuming each ab [op] cd = x takes at least 7 tokens, that gives a testing budget of 1100 combinations, which means we can only enumerate over 6 distinct symbols at most (6! = 720, 7! = 5040, only two problems of 823 have <=6 distinct symbols). To save training tokens during the experimental process, I noticed that I could focus on one domain at a time. For example, I could train and validate just on text cipher. This was very useful before coming to bit manipulation since the other categories required far fewer tokens to train.

Tinker vs Megatron-Bridge training infrastructure

My early experiments ran on Tinker, but switching to Megatron-Bridge turned out to matter a lot: in one run, changing nothing but the backend raised bit manipulation accuracy from 0.81 to 0.89 (against a synthetic-trace ceiling of 0.91 for the category at the time). The reason is that a Tinker LoRA requires a lossy SVD to be converted into the PEFT format, whereas a Megatron-Bridge LoRA maps to PEFT exactly.

Late in the competition, I discovered a bug in my code that converts the Megatron-Core distributed checkpoint into a HF PEFT adapter. I caught it late because my internal validation scores stayed high despite it, and fixing it made little difference: public LB went 0.884 -> 0.880 and private LB stayed 0.908. Megatron stores a fused QKV projection for the attention layers, and my extractor split the B LoRA matrix into separate q/k/v with a plain contiguous slice, whereas Megatron interleaves Q/K/V per query group. The bug thus mixed up Q, K, and V rows. I find it strange that my internal validation was still so high even with this bug. I can only hypothesize that most of the adaptation lives in other layers, especially the MoE layers.

Conclusion

Storage: facts the weights can memorize during training (e.g. the bit manipulation signatures, text cipher words).

Compute: each reasoning step should use inputs that are already explicitly in the trace. The smaller the positional distance between an input and the step that consumes it, the better.

### 3rd Place Solution

来源：https://www.kaggle.com/competitions/nvidia-nemotron-model-reasoning-challenge/discussion/709136

Overview

My overall solution is SFT on deterministic reasoning traces produced by problem specific solvers. The reasoning traces are designed such that the final answer can be reached from the problem statement step-by-step without any hidden deduction or “jumps”.

It builds on top of the excellent early work and ideas from llkh0a, huikang, kemshim, youkinasa and others, with the following improvements:

Rewritten numeric solver that is more minimal and with a better guessing logic

Hui Kang-style bit manipulation trace compacted with hex notation and extended with majority operation search

Data augmentation for all problem types except gravity, unit conversion and numeral

Constraint satisfaction problem / CSP-like algorithm that solves overall 24.2% of cryptarithm problems within token budget (27.8% of deduce cases, 9.8% of guess cases) using multiplication patterns and backtracking search

Two stage training approach that decouples memorization and execution to help model learn the cryptarithm trace better

Local validation strategy that turns out to track the private test set well

Solver and trace design

Gravity, Unit conversion, Numeral

These are the trivial categories that the model can do very well with minimal training. I reused the traces from llkh0a's notebook directly.

Cipher

I simplified the trace from the same notebook and removed the elaborate analysis on missing letters. I found that simply adding more augmented samples is sufficient to teach the model to fill in missing letters due to the small vocab size involved.

Bit manipulation

I modified Hui Kang-style bit manipulation trace slightly with the following changes:

The first change is to use hex-notation with tail bits to more compactly represents output bit columns.

This brings about 25% reduction in token usage, and allows the second change: search over majority operation (MAJ) to fit under token budget.

Lastly, I changed the solver's rule ordering so OR-NOT candidates are tried before plain OR and XOR:

Default rule ordering: Identity, NOT, Constant, AND, OR, XOR, AND-NOT, OR-NOT, XOR-NOT, MAJ

New ordering: Identity, NOT, Constant, AND, OR-NOT, OR, XOR, AND-NOT, XOR-NOT, MAJ

which empirically improves the solve rate slightly (0.6%).

Numeric equation

After solving a number of numeric equation puzzles manually, I found that there are two underlying structures governing the equations:

"simple": f(a,b) = fmt(op(a,b))

"reverse": f(a,b) = fmt(rev(op(rev(a),rev(b))))

where op refers to a hidden operation represented by the operator symbol, rev means reversing the digits, and fmt means formatting negative answers using the optional pre or post negative markers.

In addition, the "simple" or "reverse" structure has to be applied globally across the equations in the same problem, rather than independently within each equation in the same problem.

I rewrote a solver for numeric equations from scratch, adding operation one by one to identify the operations that are truly needed to solve all the problems. I arrived at this set of operations:

[
 "a+b",
 "a-b",
 "abs(a-b)",
 "negated absolute diff",
 "b-a",
 "a*b",
 "a+b+1",
 "a+b-1",
 "a*b+1",
 "a*b-1",
 "concat(a,b)",
 "concat(b,a)",
 "max(a,b) mod min(a,b)",
]

I think this is the exact set of operations that should be searched over and nothing more, since if the solver were allowed to "peek" at the answer by including the question as an example, all of the problems can be solved without any ambiguity (i.e. with one unique solution).

Without peeking at the answer, sometimes there can be multiple operations that happen to fit all the examples. This happens only for the subtraction type operations: conflicts occur frequently between ['a-b', 'negated absolute diff'], ['abs(a-b)', 'a-b'], etc. I haven't found a way to disambiguate that is better than random guess, so I choose the above deterministic ordering (e.g. preferring a-b over negated absolute diff) to maximize the solve rate on the training numeric problems.

There are more interesting patterns. For example, this is a tabulated co-occurrence counts between pairs of true operations within each problem:
[图 1: inbox%2F91259%2F6017e38a46b12b9e8656a08e95ec3bf5%2Fnumeric-op-crosstab.png]

The organized patches of zeros in the table shows a clear pattern: a*b never appears together with a*b-1 or a*b+1 in the same problem; a+b never appears together with a+b-1 or a+b+1, etc. This suggests that in the data generation process, there are broad "families" of operations that the data generator will sample from, and within each sampled family only one operation will be chosen. I used this to improve the guessing logic when the question's operator is unknown: the optimal guess is an operation in a family that has not been mapped yet in the existing examples.

Using the above findings, I implemented the following strategy:

Tries two structures in this order

"simple": f(a,b) = fmt(op(a,b))

"reverse": f(a,b) = fmt(rev(op(rev(a),rev(b))))

For each structure

Go through each operator symbol

Test candidate operation in the above order

Find the first candidate operation that fits every example answer pairs with this operator

Exit early if any operator cannot be explained, this means the structure is incorrect

Prefer "simple" over "reverse" if both fully explains all observed operators

If the question's operator is unseen, guess in this priority: a-b, a+b, a*b, choosing the unseen operation type

With this solver, the solve rate ceiling for the training data is:

deduce: 559 / 596 = 93.79%

guess: 53 / 136 = 38.97%

overall: 612 / 732 = 83.61%

Cryptarithm

My strategy for cryptarithm is inspired by the multiplication pattern lookup ideas floated around in the discussions by kemshim and youkinasa. The idea is to use multiplication examples to propagate constraints and provide a good starting point for backtracking solver with most of the digits already solved.

Pattern lookup table

An encrypted equation such as {!*{| = ]!]] can be normalized to a "signature" that describes how different symbols relate to each other, in this case:

{!*{| = ]!]] -> ab-ac-dbdd

There are exactly 2 of them. From this table, the raw symbols corresponding to abcd must be either 2674 or 9321. Looking at each individual column gives the possible digits for each symbol (e.g. b -> ! has to be either 6 or 2).

With this lookup table, we can quickly narrow down the set of possible digit mappings based on just the signature. This is especially true if there are multiple equations that need to be satisfied simultaneously, since many digit mappings become invalid due to conflicts.

I pre-computed the lookup table by enumerating all 100 * 100 two-digit operand pairs under both structures (simple and reverse) and the three multiplication-family operations (a*b, a*b+1, a*b-1), each yielding a signature. Candidate digit mappings are recorded for each (signature, structure, multiplication type) combination.

I focus on multiplication-family operations because they constrain more symbols than addition or subtraction. In the multiplication-family lookup, there are 3,678 unique signatures and 11,334 non-empty (signature, structure, multiplication type) triples.

Cryptarithm strategy

Assuming we can recall information from the pattern lookup table perfectly, we can solve a subset of cryptarithm problems using this strategy:

Identify multiplication (MUL) examples

Each MUL example emits the following from the pattern lookup table:

Possible digits for each symbol

Possible candidate mappings

When there are more than one MUL examples, compute their intersection.

Intersection finding requires "joining" candidate mappings from different MUL examples

Two (or three, up to four) candidate mappings can either be merged (no conflict at all) or rejected due to conflict

The result of the intersection is a much more constrained set of possible candidate mappings, at this point often exactly 1, since most will be rejected due to conflicts. Let's call each of these merged candidate mapping an anchor mapping.

For each anchor mapping, launch a backtracking symbolic solver to solve for the remaining unknowns over the free digits

At each step, choose the example with the least number of unknowns and solve that equation

For non-negative answers, try a+b, a+b+1, a+b-1, a-b, abs(a-b)

For negative answers, try a-b, -abs(a-b), b-a

Backtrack when no valid solution can be found

Stop early once all unknowns are solved

The above steps are repeated for each (structure, multiplication type) pairs, where structure can be simple or reverse, and multiplication type can be a*b, a*b+1, a*b-1. The algorithm greedily tries reverse first, then simple, and stops early whenever it finds a solution that satisfies all the examples.

My symbolic solver supports up to 2 unknowns per equation for simplicity. Even this is sufficient to solve a non-trivial number of problems as the anchor finding phase is often doing most of the heavy lifting.

More implementation details

Candidate mapping enumeration is capped at 48 per signature

Maximum number of allowed anchor mapping is 8. Increasing this further doesn't improve solve rate under budget.

If there are examples with length 3 answers that share the same operator as MUL examples, they should be treated as MUL examples as well.

When there is a single unmapped question symbol and a single unmapped digit, the last step will establish the mapping between the two so the question can be answered.

For questions with unknown operators, the solver applies the same guessing logic as numeric equations: choose an operation from the unused operation family

The tags <RECALL_DOMAINS> and <RECALL_ROWS> are for anticipating sections in the trace that should be derived purely from memory. More on this later in the modeling section.

Cipher

I generated 3K additional augmented samples, sampling from the sentence structures and pool of words uniformly.

Bit manipulation

I augmented new problems for bit manipulation using two methods:

Swap-augment: pick an existing problem in the original dataset, change the input values for each example (including question example) and apply the underlying transformation to get new output values. Then, shuffle the new examples and select a new question.

Formula-augment: Construct completely new bit manipulation problems using two-ops / three-ops / majority / choice structures.

In the final dataset, I constructed 3K swap augmented samples and 3K formula augmented samples. Each sample is duplicated twice.

Numeric equation

To create a new numeric equation problem, I sample a random original problem from a pool of source problems consisting of the original numeric problems and decrypted cryptarithm problems. For each example in this sampled problem, I change the operands with new random values and compute the updated answer. The operator symbols are changed too. This produces a new numeric equation problem.

The reason for doing this rather than creating completely new problems is that I don't want to accidentally create new artifacts or remove underlying structures hidden in the data. This can happen if my own generator differs too much from the official generator.

My final dataset contains all the original numeric problems, decrypted cryptarithm problems, and 3K augmented samples.

Cryptarithm

To create a new cryptarithm problem, I first create a new numeric equation problem as per the previous section. Then, I apply a cipher encryption on this new numeric problem, which yields a new cryptarithm problem.

This is the category that needs the most number of augmented samples. My final dataset consists of 48K augmented cryptarithm samples, of which 4K samples are of concat type (that can be answered directly without going through the pattern matching path).

Second stage: learning to solve

The resulting LoRA adapter becomes the initial LoRA adapter in the second stage training, which uses the actual trace data for the tasks as per the previous section. During second stage training, the model can then focus on learning the execution: how to compose the already memorized patterns to arrive at the final solution. A small number of drill style samples (3K) are injected in the data mix to help the second stage model retain memory.

Two stage training appears to be more sample efficient. I experimented with training on 12K cryptarithm samples and check the solve count in the held out validation set. There are about 11 non-concat cryptarithm problems that are solvable under budget.

Direct training: solved 0/11

Two stage training: solved 7/11

This allows the cryptarithm trace to be more or less learned (achieving near the target solve rate) with 40K+ samples. One important observation is that first stage training doesn't seem to impair the model's ability to learn the actual downstream tasks.

Two stage training is also more modular: any unrelated changes to solver logic or trace format can reuse the same first stage model without having to memorize from scratch again.

Validation strategy

The validation strategy is quite simple: hold out about 10% of data for validation, stratified by problem category. This yields 954 validation rows.

When training, I excluded rows belonging to the validation set from training data. For augmented samples, if the augmented sample is derived from an original problem in the validation set, the augmented sample is also excluded from training data. This reduces the chance of any subtle leakage during validation.

The validation strategy turns out to track the private test scores well, but not the public leaderboard scores. The wall at 0.86 is clearly visible on the public LB. One of my 0.85 public LB submissions has a score of 0.90 on the private LB.

Additional metrics

In addition to the official evaluation metric (% of tasks solved), I also track the following metrics:

Perfect trace rate:

This tracks whether the model is emitting the expected trace exactly. Sometimes the model can get the correct answer by luck but still make mistakes in parts of the trace. This is a leading indicator intended to catch that before it affects solve rate.

I try to keep this >85% for bit manipulation, and >95% for cipher and numeric equations.

For gravity and unit conversion involving floating point arithmetic, this metric is expected to be low. This is fine since the accuracy for those tasks are very high despite not emitting the exact trace matching the floating point decimals.

Cryptarithm pattern matching specific metrics: I compute metrics to track how well the model recall the memorized domains and rows, and how self-consistent the trace is assuming the recalled memories are correct.

Iterating with single-category training

When testing a new solver logic or trace format, I try to train and validate on just the target category to isolate the effects of the change. I treat standalone validation scores as the ceiling that can be achieved because usually there will be a slight accuracy drop when the same variant is trained with all other categories.

Once I confirm that a new variant is indeed better in terms of standalone validation scores, I include it in the final mix. If the metrics in the all-categories run drop too much compared to the standalone run, I treat it as a signal to add more augmented samples.

### 18th solution: From Deterministic Solvers to Learnable Reasoning Traces

来源：https://www.kaggle.com/competitions/nvidia-nemotron-model-reasoning-challenge/discussion/715330

Overview

First of all, we would like to thank Kaggle and NVIDIA team for hosting the Nemotron Model Reasoning Challenge, and also thank the community and open-source participants. Our solution was built on top of the open-source deterministic CoT pipeline from tonghuikang/nemotron. The public solutions and discussions after the competition also helped us understand the gap between our work and the strongest teams more clearly.

Our team won a gold medal in this competition. Considering several major mistakes in our process, especially the lack of a reliable local validation set, we were quite lucky to still finish in the gold-medal range. Congrats to @kevin1742064161 and @quincyqiang for becoming Kaggle Grandmasters with this gold medal, and congrats to @forcewithme for a 2x Kaggle Grandmaster.

At a high level, our approach treated the model as a calculator that needed to be taught fixed algorithms. For each puzzle category, we wrote deterministic reasoners to compute answers and generate teacher chain-of-thought traces, then distilled these traces into a rank-limited LoRA adapter through SFT. Under this framework, the score was mainly determined by two factors:

how many real problems the reasoners could solve;

whether the generated CoT traces were short, consistent, local, and easy for the model to imitate.

One lesson we shared with many top teams was that a CoT trace should be a learnable trajectory, not merely a record proving that a solver can run through the problem. A high-quality trace should be short, consistent, local, free of hidden computation, complete in its references, and each step should follow from small rules already introduced in the context. The key question is not only whether the solver itself is correct, but whether the trajectory is easy for the model to learn.

Our Biggest Mistake: No Local Validation Set

Our biggest mistake was that we did not build a local validation set early enough. This was the root cause of almost no real progress during the last two months.

We did not realize early how small and noisy the test set was. At the same time, we did not put synthetic problem generation at a high enough priority. As a result, we trained on the full dataset throughout the competition and used the public leaderboard as our validation signal.

This caused two serious problems.

First, after our public LB reached around 0.87, our exploration became scattered. We tried many directions, but most of them were not continued deeply. For example, the synthetic-data direction in expv003 was only tried once and then abandoned because its public score looked worse at that time. However, from the private leaderboard, the improvement was actually quite meaningful.

Second, we failed to select the highest-private submissions. From the top1 solutions after the competition, local validation scores, public scores, and private scores did have a certain level of consistency. If we had built a trustworthy local validation set, we likely would have made better submission-selection decisions.

We also clearly acknowledge the gap between us and the top six teams. Their solutions showed stronger validation discipline, more systematic synthetic data, and more complete exploitation of the benchmark structure. We learned a lot from them after the competition.

Solution

The writeups only keep the valuable experiment versions. In practice, these versions skipped many abandoned trials. For clarity, we uniformly name the important experiments as expv001 to expv006, and describe the final LoRA fusion submission as expv001_002.

expv001: Early Stable Baseline

Score gain in one sentence: expv001 established a stable 0.87-level baseline by improving the early deterministic reasoners while keeping the CoT style short and consistent.

expv001 was our first reliable improvement over the open-source baseline, and it became the reference point for later experiments. It kept the overall framework for all nine official categories: each problem was processed by its corresponding reasoner, which generated a CoT and a final answer, and all samples were included in the training corpus without filtering by whether the rule was explicitly found.

The main changes were:

cryptarithm: a backtracking solver assigned digits to symbols, tried operator rules such as addition, absolute difference, multiplication, concatenation, and reverse concatenation, then checked whether all examples were mutually consistent. The search budget was still conservative, so coverage was not high, but the generated CoTs were short and stable.

bit_manipulation: the solver already included whole-byte-level pattern search, while avoiding later complicated ambiguous fallback ordering.

equation_numeric: the solver included early fixes for negative signs, reversal, zero padding, and operator-prefix/operator-suffix output formats.

cipher, gravity, numeral, and unit_conversion: these categories mostly followed the stable official rules and were already close to perfect locally.

expv002: Larger Search Budget and Whole-Byte Logical Shifts

Score gain in one sentence: expv002 improved hard cryptarithm and bit cases by increasing cryptarithm search budget and adding whole-byte logical shift rules for bit manipulation.

Cryptarithm had the highest failure rate among the nine categories. Its solver used backtracking: it assigned a digit from 0 to 9 to each symbol, tried a rule for each operator, and verified whether all examples were mutually consistent. Real tasks often had only three to five examples but more than ten unresolved symbols, so the search space was enormous. Many failures were timeouts rather than truly unsolvable cases. We therefore doubled the search budget for each phase, allowing the solver to recover some difficult cases that had previously timed out.

For bit manipulation, the original whole-byte mode recognized cyclic shifts but not logical shifts. The two operations are different: cyclic shifts wrap discarded bits to the other side, while logical shifts discard them and pad with zeros. Without logical shifts, tasks whose rule was a pure shift or shift plus XOR mask would be missed. We added whole-byte logical shifts for left and right shifts by 1 to 7 bits, with an optional XOR mask, and placed this rule after rotate rules to reduce interference with true cyclic-shift cases.

We did not add subtraction-style cryptarithm operators at this stage because the dataset answers were pure digit strings and did not provide a clean negative-number encoding. Equation was already relatively stable, so this experiment focused on cryptarithm and bit manipulation.

expv003: Synthetic Problem Generation

Score gain in one sentence: expv003 improved private performance by adding controlled synthetic problems that were generated from hidden rules and filtered by deterministic reasoners.

The synthetic pipeline generated additional training samples for three target categories:

bit_manipulation

equation_numeric_deduce

cryptarithm_deduce

Each synthetic problem followed the same structure:

choose a hidden transformation rule;

sample several distinct inputs;

apply the hidden rule to create examples;

reserve one more input as the query;

compute the final answer using the same rule;

validate structural consistency;

keep the sample only if the existing deterministic reasoner solved it correctly.

For bit_manipulation, the generator created 8-bit binary-string transformation tasks such as XOR with a constant, rotate left/right, and rotate followed by XOR. For equation_numeric_deduce, it generated custom-operator arithmetic tasks using rules such as addition, subtraction, reverse subtraction, multiplication, and absolute difference. For cryptarithm_deduce, it generated symbolic arithmetic tasks with a one-to-one digit-symbol mapping and simple concatenation or reverse-concatenation rules.

The important point is that these samples were not random benchmark-style text. Each accepted sample had a known hidden rule, a recomputed answer, and a reasoner check. This made the synthetic data closer to clean deduction problems.

In this version, we generated 400 bit_manipulation problems, 1,400 equation_numeric_deduce problems, and 1,400 cryptarithm_deduce problems, then merged them into the training mix. In retrospect, this direction deserved much more effort. We stopped after an early version because the public score did not look promising enough, but the private score showed that synthetic data was likely important.

expv004: Answer-Guided Selection of Rule and Format

Score gain in one sentence: expv004 produced cleaner labels for equation and cryptarithm by selecting among rule-format candidates whose rendered answer exactly matched the ground truth.

This version turned scattered answer-guidance ideas into a unified label-generation mechanism for the equation and cryptarithm families.

The pseudo-equation tasks had many possible variants: forward concatenation, reverse concatenation, disguised addition, disguised multiplication, reverse subtraction, leading-zero preservation, digit-wise operations, and formats where the operator symbol appeared as a prefix or suffix in the result.

Instead of committing to one rule first and hoping it was correct, this version expanded the full candidate space:

arithmetic operator;

operand and result reversal;

plain digit output;

operator prefix or suffix;

trailing minus sign;

zero padding and signed zero padding.

It then selected candidates whose rendered result exactly matched the ground-truth answer. When multiple candidates matched, we chose the easiest-to-learn explanation using priors: plain output first, natural operator meanings first, and no reversal before reversal.

For cryptarithm guess cases, where the query operator might not appear in the examples, the CoT explicitly stated that the prompt could not uniquely determine the hidden operator, then selected a rule family consistent with the answer. This produced some of our cleanest teacher labels for the hardest guess-style tasks.

expv005: No-GT Solve-Rate Improvement

Score gain in one sentence: expv005 improved the local solve count without using gold answers to lock rules, mainly through broader candidate search and deterministic fallback ordering.

The goal of expv005 was to improve real-problem CoT coverage as much as possible without using the gold answer to choose the rule.

For bit_manipulation, we added fallback candidate search on top of official rules. The solver first found all bit-level candidates that could explain the examples. If the query-bit result was not unique, it used deterministic prior and fallback ordering to select one candidate. The gain came from example-supported candidate rules plus fixed ordering, not from back-solving the answer.

For equation_numeric_deduce, the solver enumerated operand parsing modes, result reversal, zero padding, symbol markers, and other output formats. It then found candidate rules that explained the examples and used a fixed ordering to choose the final one. equation_numeric_guess remained conservative and avoided query-only answer fallback.

For cryptarithm, the main improvement came from a more expensive search and refreshed CoT generation for cryptarithm categories. This increased local coverage, especially for cryptarithm_deduce.

expv006: Conservative GT-Assisted Score-Pushing

Score gain in one sentence: expv006 raised local solve rate and private score by using gold answers only to choose among example-consistent candidates, instead of directly constructing answers from gold.

expv006 started from the expv005 direction and enabled conservative gold assistance. This version no longer claimed to be no-GT. Its purpose was to push the score and understand the upper bound of answer-assisted teacher labels.

The principle was: first use examples to find a set of candidate rules that already explain the examples; if multiple candidates were plausible, then use the gold answer to choose the candidate that produced the correct query answer. It did not create a brand-new rule from the gold answer.

For bit_manipulation, the solver kept the candidate-search framework from expv005, but allowed the gold bit to choose among multiple example-consistent candidates.

For equation_numeric_deduce, gold was used only to break ties among candidates that already explained the examples. equation_numeric_guess avoided direct query-only gold fallback and used conservative symbol priors and default rules.

For cryptarithm_deduce, candidate-level gold tie-break and gold guard helped avoid training on symbolic candidates whose query answer disagreed with the true answer. Direct query-gold re-encoding was disabled. cryptarithm_guess kept symbol priors but avoided directly wrapping the gold answer as if it had been reasoned out.

expv001_002: LoRA Fusion

Score gain in one sentence: expv001_002 improved the final submission by merging two LoRA adapters at the weight level and projecting the merged update back to a valid rank.

Besides single-reasoner iterations, we also used LoRA fusion. Different experiments were good at different task types, so merging their adapters could combine complementary strengths without retraining.

A LoRA adapter represents a low-rank update to the base model weights:

Delta W = (alpha / r) * B * A

To merge two adapters, we first restored each adapter to its true scale using its own alpha and rank, then linearly combined their updates with equal weights. The competition imposed a rank limit, so direct concatenation of two rank-32 adapters would exceed the limit. Instead, after combining the low-rank factors, we applied truncated SVD and projected the merged update back to a valid target rank. This produced a single legal LoRA adapter.

We also tried TIES and DARE merging, but our own SVD-based LoRA fusion performed better. The final selected gold-medal submission used the fusion of expv001 and expv002, named expv001_002.

reasoner 能解出多少真实题；

我们和很多前排队伍共有的一个经验是，CoT trace 应该是一条可学习轨迹，而不仅仅是证明 solver 能跑通问题的记录。高质量 trace 应该短、一致、局部、没有隐藏计算、引用完整，并且每一步都应该能从上下文里已经引入的小规则推出。关键问题不只是 solver 本身是否正确，而是这条轨迹是否容易被模型学习。

我们最大的失误：没有线下验证集

我们最大的失误是没有足够早地构建线下验证集。这是最后两个月几乎没有真正进展的根本原因。

我们没有很早意识到测试集有多小、有多噪。同时，我们没有把合成题目生成放在足够高的优先级。结果是，我们从头到尾都在全量数据上训练，并把 public leaderboard 当作验证信号。

这导致了两个严重问题。

第一，在我们的 public LB 到 0.87 左右之后，我们的探索变得很发散。我们尝试了很多方向，但大多数方向都没有持续深入。比如 expv003 的合成数据方向只尝试了一版，然后因为当时 public 分数看起来更差就放弃了。但是从 private leaderboard 看，提升其实相当有意义。

第二，我们没有选到 private 最高的提交。从赛后的 top1 solutions 看，线下验证分数、public 分数和 private 分数之间确实存在一定一致性。如果我们有一个可信的线下验证集，我们很可能会做出更好的提交选择。

方案细节

writeups 只保留了有价值的实验版本。实际上，这些版本跳过了很多被废弃的尝试。为了清晰起见，我们统一把重要实验命名为 expv001 到 expv006，并把最终 LoRA 融合提交描述为 expv001_002。

expv001：早期稳定基线

一句话上分点： expv001 通过改进早期确定性 reasoner，同时保持 CoT 风格短且一致，建立了一个稳定的 0.87 档基线。

expv001 是我们相对于开源 baseline 的第一个可靠提升版本，也成为后续实验的参照点。它保留了九个官方类别的整体框架：每道题由对应 reasoner 处理，生成 CoT 和最终答案，并且所有样本都进入训练语料，不按照规则是否被显式找到来过滤。

主要变化是：

cryptarithm：回溯 solver 为符号分配数字，尝试加法、绝对差、乘法、拼接、反向拼接等 operator rule，然后检查所有 examples 是否互相一致。搜索预算仍然保守，所以覆盖率不高，但生成的 CoT 短且稳定。

bit_manipulation：solver 已经包含整字节级别的模式搜索，同时避免后续更复杂的 ambiguous fallback 排序。

equation_numeric：solver 包含了负号、反转、补零、operator 前缀/后缀输出格式的早期修复。

cipher、gravity、numeral、unit_conversion：这些类别基本沿用稳定的官方规则，本地已经接近或达到满分。

expv002：更大的搜索预算和整字节逻辑移位

一句话上分点： expv002 通过增加 cryptarithm 搜索预算，并为 bit manipulation 加入整字节逻辑移位规则，改善了困难 cryptarithm 和 bit 样本。

cryptarithm 是九个类别中失败率最高的。它的 solver 使用回溯：为每个符号分配 0 到 9 的数字，为每个 operator 尝试一条规则，并验证所有 examples 是否互相一致。真实任务经常只有三到五条 examples，但有十个以上未确定符号，因此搜索空间巨大。很多失败是超时，而不是真正无解。因此我们把每个阶段的搜索预算翻倍，让 solver 能找回一部分以前超时的难题。

对于 bit manipulation，原始整字节模式能识别循环移位，但不能识别逻辑移位。这两个操作不同：循环移位会把被移出的 bit 绕到另一侧，而逻辑移位会丢弃它们并补零。没有逻辑移位时，规则为纯 shift 或 shift 加 XOR mask 的题会被漏掉。我们加入了左移和右移 1 到 7 位的整字节逻辑移位，并支持可选 XOR mask，同时把这个规则放在 rotate 规则之后以减少对真实循环移位样本的干扰。

我们在这个阶段没有加入 subtraction 风格的 cryptarithm operator，因为数据集答案是纯数字串，没有干净的负数编码。Equation 当时已经相对稳定，所以这个实验集中在 cryptarithm 和 bit manipulation。

expv003：合成题目生成

一句话上分点： expv003 通过加入从隐藏规则生成、并由确定性 reasoner 过滤的受控合成题目，提高了 private 表现。

合成管线为三个目标类别生成额外训练样本：

bit_manipulation

equation_numeric_deduce

cryptarithm_deduce

每个合成题目都遵循相同结构：

选择一个隐藏变换规则；

采样几个不同输入；

应用隐藏规则生成 examples；

额外保留一个输入作为 query；

用同一规则计算最终答案；

验证结构一致性；

只有当现有确定性 reasoner 正确解出它时才保留样本。

对于 bit_manipulation，generator 创建 8-bit 二进制字符串变换任务，例如与常量 XOR、左/右 rotate、rotate 后 XOR。对于 equation_numeric_deduce，它生成自定义 operator 算术任务，规则包括加法、减法、反向减法、乘法和绝对差。对于 cryptarithm_deduce，它生成带有一一对应数字-符号映射的符号算术任务，以及简单拼接或反向拼接规则。

重要点是，这些样本不是随机的 benchmark 风格文本。每个被接受的样本都有已知隐藏规则、重新计算的答案，以及 reasoner 检查。这使合成数据更接近干净的 deduction problem。

这个版本中，我们生成了 400 道 bit_manipulation、1,400 道 equation_numeric_deduce 和 1,400 道 cryptarithm_deduce 题目，然后把它们合入训练 mix。回头看，这个方向值得投入更多精力。我们在早期版本后就停止了，因为 public 分数看起来不够好，但 private 分数显示合成数据很可能很重要。

expv004：答案引导的规则和格式选择

一句话上分点： expv004 通过在渲染答案与真值完全匹配的 rule-format 候选中进行选择，为 equation 和 cryptarithm 生成了更干净的标签。

这个版本把零散的答案引导想法转化为 equation 和 cryptarithm 家族的一套统一标签生成机制。

伪等式任务有很多可能变体：正向拼接、反向拼接、伪装加法、伪装乘法、反向减法、保留前导零、逐位运算，以及 operator 符号作为结果前缀或后缀出现的格式。

这个版本不再先承诺一条规则然后希望它是对的，而是展开完整候选空间：

算术 operator；

operand 和 result 反转；

纯数字输出；

operator 前缀或后缀；

末尾负号；

补零和带符号补零。

然后它选择渲染结果与 ground-truth answer 完全一致的候选。当多个候选都匹配时，我们用 prior 选择最容易学习的解释：纯输出优先、自然 operator 含义优先、不反转优先于反转。

对于 cryptarithm guess 样本，也就是 query operator 可能没有出现在 examples 中的样本，CoT 会明确说明 prompt 无法唯一确定隐藏 operator，然后选择一个与答案一致的规则族。这为最困难的 guess 风格任务产生了我们最干净的一批教师标签。

expv005：No-GT 求解率提升

一句话上分点： expv005 在不使用 gold answer 锁定规则的情况下，主要通过更广的候选搜索和确定性 fallback 排序，提高了本地 solve count。

expv005 的目标是在不使用 gold answer 选择规则的前提下，尽可能提高真实题 CoT 覆盖率。

对于 bit_manipulation，我们在官方规则之上加入 fallback candidate search。solver 首先找到所有能解释 examples 的 bit-level candidate。如果 query-bit 结果不唯一，它就用确定性 prior 和 fallback ordering 选择一个候选。提升来自 examples 支持的候选规则加固定排序，而不是从答案反推。

对于 equation_numeric_deduce，solver 枚举 operand 解析方式、result 反转、补零、符号 marker 和其他输出格式。然后找到能解释 examples 的候选规则，并用固定排序选择最终规则。equation_numeric_guess 保持保守，并避免 query-only answer fallback。

对于 cryptarithm，主要提升来自更昂贵的搜索，以及对 cryptarithm 类别刷新 CoT generation。这提高了本地覆盖率，尤其是 cryptarithm_deduce。

一句话上分点： expv006 通过只在 example-consistent candidates 中使用 gold answer 做选择，而不是直接从 gold 构造答案，提高了本地求解率和 private 分数。

原则是：先使用 examples 找到一组已经能解释 examples 的候选规则；如果多个候选都合理，再用 gold answer 选择能产生正确 query answer 的候选。它不会从 gold answer 创造一条全新的规则。

对于 equation_numeric_deduce，gold 只用于在已经解释 examples 的 candidates 中打破平局。equation_numeric_guess 避免直接 query-only gold fallback，而使用保守的 symbol prior 和默认规则。

对于 cryptarithm_deduce，candidate-level gold tie-break 和 gold guard 帮助避免训练那些 query answer 与真实答案不一致的 symbolic candidates。直接 query-gold re-encoding 被关闭。cryptarithm_guess 保留 symbol prior，但避免直接把 gold answer 包装成像是推理出来的结果。

一句话上分点： expv001_002 通过在权重层面融合两个 LoRA adapters，并把合并后的 update 投影回合法 rank，改善了最终提交。

除了单 reasoner 迭代，我们还使用了 LoRA fusion。不同实验擅长不同题型，所以融合它们的 adapters 可以在不重新训练的情况下结合互补能力。

一个 LoRA adapter 表示的是对 base model weights 的低秩更新：

Delta W = (alpha / r) * B * A

### 10th Place Solution

来源：https://www.kaggle.com/competitions/nvidia-nemotron-model-reasoning-challenge/discussion/708535

Many thanks to NVIDIA and the Kaggle staff for organizing the Nemotron Model Reasoning Challenge, and congratulations to everyone who placed. This was a great competition to work on, and I learned a lot from building a fully deterministic data pipeline around a single base model.

Overview

Our solution was based on deterministic program-generated reasoning traces rather than LLM distillation. For each task category, we built symbolic reasoners that derive answers from the prompt alone, then fine-tuned a single base model to imitate those reasoning procedures.

Method

Program-based deterministic reasoners generate Chain-of-Thought (CoT) traces for synthetic problems across 9 task categories.

Each reasoner re-derives the answer from the prompt alone. It never reads the ground-truth answer and emits a step-by-step CoT ending in \boxed{answer}.

We then SFT a single base model with LoRA on those traces so it learns the reasoning procedure, not just the answer.

Base model

nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16
30B Mixture-of-Experts, approximately 3B active parameters.

Scores

Public LB: 0.860

Private LB: 0.880

Placement: 10th

The main lesson was that the final score was mostly limited by the quality and coverage of the deterministic teachers. Once the traces were clean, compact, and consistent, the model could imitate them surprisingly well.

Core idea — Synthetic data + procedure learning

Each category has a program-based deterministic reasoner that re-derives the answer from the prompt alone. The stored answer is never used during trace generation. The generated trace explains the procedure step by step and ends with \boxed{answer}.

The corpus tokenizes each example with the chat template, masks the prompt tokens with mask=0, and trains only on the completion tokens with mask=1. This lets the LoRA adapter learn the generated reasoning procedure rather than only the final answer.

A useful working assumption was that, given clean and consistent traces, SFT could imitate the teacher reasoner closely. Therefore, validation accuracy was largely bounded by the reasoner's own oracle accuracy. The main lever was improving the coverage and learnability of the generated traces, rather than relying on SFT hyperparameter tricks.

Main reasoner improvements

The largest gain came from bit_manipulation, where the reasoner was rewritten to match the true task structure more closely. A smaller but important improvement came from equation_numeric, where candidate ordering and unseen-operator guessing were improved using corpus statistics.

bit_manipulation trace update

The main reasoner change in this solution was to rewrite the bit_manipulation generator from a per-bit logical-operation matcher into a rotate/shift key-table reasoner.

This improved reasoner oracle accuracy from 1364/1602 = 85.14% to 1582/1602 = 98.75%, while replacing long, loop-prone traces with shorter derivations that were easier for the model to copy.

Background

The original generator modeled every output bit as a logical operation over fixed input columns. For each output column, it searched candidate families such as Identity, NOT, constant 0, constant 1, AND, OR, XOR, AND-NOT, OR-NOT, and XOR-NOT.

It then found operand pairs whose columns reproduced the output, built left and right stride runs, truncated them to eight bits, and filled the middle slots by a category vote.

This representation did not match the actual task structure well. The underlying transform was a rotate-and-shift composition rather than arbitrary per-bit boolean logic over fixed columns. As a result, many problems could not be expressed well by the old family search, which limited the oracle ceiling to 1364/1602 = 85.14%.

The traces were also long and enumeration-heavy, with repeated Left, Right, Best, Truncated, Tentative, Preferred, and Matched sections. These traces were difficult for the model to imitate reliably and sometimes encouraged runaway generation loops.

Key-table reasoner

The reasoner was redesigned around the rule that generates the data:

out[i] = F(rotl(x, a)[i], shl(x, b)[i], shr(x, c)[i])

Here:

rotl is the input rotated left by a, where a ranges from 0 to 7.

shl is the input shifted left by b, where b ranges from 1 to 7 with zero fill.

shr is the input shifted right by c, where c ranges from 1 to 7 with zero fill.

F is a shared 3-input boolean function used for every bit.

Instead of naming F, the reasoner reads it from the examples as a key table that maps each 3-bit key to an output bit.

The offsets (a, b, c) are recovered from boundary bits where one operand is forced to zero. At bit 0, shr = 0; at bit 7, shl = 0. Therefore, each boundary output column must be a function of only two input columns. Scanning single columns and column pairs at these boundaries constrains (a, b) from bit 0 and (a, c) from bit 7.

Each surviving candidate (a, b, c) is then verified against every example. The reasoner accumulates the key table example by example and rejects a candidate as soon as a conflict appears. The first candidate whose table covers all keys needed for the question is selected.

Ties and uncovered keys fall back to agreement, where the same prediction must appear twice and unknown values are filled with 1, or to a per-bit majority vote. The stored answer is never used during this process.

Trace efficiency

The trace was shortened without changing any answers.

Redundant per-example bit echoes were removed because verification only needs the transposed columns. The candidate List: enumeration was also removed, since it was the largest source of long traces and often caused runaway generation loops. The candidate walk now iterates the set directly.

Additional boundary scans for bits 1 and 6, then bits 2 and 5, are only run when the candidate set is large. This is gated by a count threshold of _THRESH = 24.

Keys are rendered compactly in key>value form.

Remaining oracle failures

The reasoner still fails on 20/1602 problems.

All 20 problems are expressible within the rotate/shift plus key-table family, so there were no failures caused by the rule being outside the reasoner's hypothesis class. The remaining failures come from ambiguity in identifying the rule from the given examples.

Of these 20 failures, 11 are inherently underdetermined. In these cases, the question requires a 3-bit key that never appears in the examples, leaving a hole in the key table. The reasoner must fill the missing value through fallback logic such as filling with 1 or using a majority vote, but the examples do not contain enough information to determine the answer uniquely.

The other 9 failures are candidate-selection errors. In these cases, at least one consistent (a, b, c) decomposition gives the correct answer, but multiple decompositions are consistent with the examples. The reasoner's selection order or fallback path chooses a different consistent candidate, leading to the wrong answer.

Token budget

Not all regenerated traces fit within an 8192-token budget. In total, 1578/1602 bit_manipulation examples were included, meaning 24 examples were dropped and did not provide training traces.

These excluded cases were mainly heavy examples with candidate explosion.

Result

Reasoner oracle accuracy improved from 1364/1602 = 85.14% to 1582/1602 = 98.75%.

On the validation subset, the reasoner was oracle-correct on 169/169 problems without introducing regressions.

equation_numeric trace update

equation_numeric asks the model to recover the rule behind an operator glyph ◯ in expressions such as:

a ◯ b = out

The glyph is arbitrary and its meaning changes per problem. There are two subtasks:

deduce — the queried glyph appears in the examples.

guess — the queried glyph does not appear in the examples.

Both changes leave the search core untouched:

deduce — reorder which candidates are tried.

guess — improve unseen-operator prediction using corpus statistics.

Three corpus observations

These observations were verified on the real data.

Operations are frequency-skewed.

add, mul, sub(a-b), and abs dominate the corpus.

 add 250
 mul 247
 sub(a-b) 233
 abs 159

The glyph - maps to signed subtraction 52% of the time, and sub outnumbers neg-abs by roughly 3:1.

Therefore, frequent and conventional operations should be tried first.

The wrapper is shared across a whole problem.

Operand reversal, result reversal, and sign formatting were shared across a whole problem in 688/688 cases.

Therefore, solving a single operator can pin the wrapper, which can then be reused for an unseen one.

Operations usually do not repeat within a problem.

Operations did not repeat within a problem in 676/688 cases.

Therefore, an unseen operator is most likely an unused operation.

deduce — fixing the candidate trial order

For deduce, the main change was to reorder candidates by frequency and to make - try conventional signed subtraction before absolute difference.

With a single example, several operations can match at once. In that case, trial order alone decides which operation is accepted.

Baseline — abs tried first:
 97-03 = 94: |97-03| = 94 match <- accepted
 97-03 = 94 match <- also correct, skipped
 apply 52-99: |52-99| = 47 <- wrong

After — '-' tries subtraction first:
 97-03 = 94: 97-03 = 94 match <- accepted
 |97-03| = 94 match <- also correct, skipped
 apply 52-99: 52-99 = -47 <- correct

Result: deduce oracle improved from 541 to 555, a gain of +14.

guess — rebuilding both axes of the guess

For guess, the queried glyph does not appear in the examples, so the reasoner must infer both:

which operation to use;

which wrapper to apply.

The output has the form:

wrapper(op(a, b))

The previous guess reasoner fixed op to absolute difference and only borrowed the wrapper from the most frequent operator. This gave 21/136 oracle accuracy. We reworked both the operation choice and the wrapper choice.

A. Choosing the operation

The operation is selected in two steps.

If the glyph has a conventional meaning, use it when available.

+ → addition

- → signed subtraction

* → multiplication

This convention is used only if no seen operator already uses that operation.

Otherwise, choose the first unused operation from the candidate trio:

 addition, absolute difference, multiplication

The order follows corpus frequency.

The difference slot here is unsigned absolute difference. For arbitrary glyphs, the result is almost always non-negative, so the unsigned form gets the sign right more often.

B. Choosing the wrapper

An unseen operator has zero examples, so its wrapper cannot be derived from itself.

Using the observation that the wrapper is shared across a whole problem, the seen operator with the most examples is solved in full to pin the wrapper. That wrapper is then reused for the unseen operator.

Skipping this step often leaves the operation right but the answer shifted, for example 4 becoming 04.

Priority samples were examples or demos associated with known fragile failure modes. They were duplicated at 2x so the model saw those traces more often without overwhelming the original distribution.

Additional techniques

Add low-logprob problems and retrain

Low-logprob problems were added or duplicated in the training corpus as priority samples, then SFT was run again.

This was not just a way to increase data volume. It was a way to re-expose traces that the model tended to forget, or traces where boundary decisions were fragile.

Demos for failure patterns, such as candidate acceptance/suppression in bit_manipulation and dictionary search in cipher, were mixed in with the same idea. The objective was to repeatedly train the reasoning steps the model was weak at and compress them into a single adapter.

Raising the LoRA alpha

To make the adapter follow the deterministic CoT more strongly, the final recipe used:

lora_alpha / r = 4

This improved CV.

Validation strategy

Held-out split

950 problems were excluded from training and used as a fixed validation set. Accuracy was tracked per category.

Oracle ceiling and fidelity

Since the model imitates the reasoner, we compared model accuracy against the reasoner's own oracle accuracy and monitored how closely the model reached that ceiling.

This made it easier to separate two failure modes:

the reasoner itself produced the wrong answer;

the model failed to imitate a correct trace.

Learnability analysis

Per-example and per-epoch log probabilities were used to identify examples and trace steps that were difficult for the model to learn.

This helped identify fragile traces that should be simplified, duplicated, or converted into targeted demos.

Iterative evaluation

Each reasoner change was evaluated per category. We checked not only the net score change, but also whether improvements in one area introduced regressions elsewhere.

Attempts that did not improve results

Curriculum learning

Easy-to-hard staged batching within each epoch was tested using difficulty bands, with noisy or mislabeled examples isolated as the final stage.

Accuracy and training stability did not change meaningfully, and no clear benefit was observed.

Two-stage training

Two-stage training was also tested by continuing from an existing adapter and fine-tuning only on targeted failure-mode demos.

Some local gains appeared, especially for y-trap-style cases, but adding stages tended to redistribute wins and losses rather than produce a robust net gain.

In the end, mixing the same demos from the start in a single-stage run was more stable, and the extra stage management did not justify itself.

3x priority duplication

Increasing priority strength to 3x overfit and reduced performance.

Priority was useful, but too large a multiplier distorted the overall training distribution.

Excluding failed or low-confidence reasoner traces

We tried excluding traces for incorrect or low-confidence problems because they were expected to negatively affect model learning.

However, accuracy decreased after removing them. This suggests that learning from failure patterns may also provide useful signal.

In the code, these low-confidence examples were often represented as rule_unknown: cases where the reasoner could not confidently identify the correct rule but still emitted a fallback trace.

Cryptarithm trace update

A large reasoner-side effort was made to generate traces not only for concat and rev_concat, but also for add, sub, and mul operations.

However, because issues such as logical jumps still occurred at a nontrivial rate, the model was not able to learn these traces stably.

LoRA merge / model merging

Model merging was tested as a way to compress complementary adapters into a single LoRA.

Both SVD merge and seed soup failed to beat the single best adapter. SVD merge could not extract complementarity within rank 32, and seed soup degraded to the level of the worst member.

Even when adapters were complementary at the output level, averaging or compressing LoRA weights tended to produce intermediate behavior rather than selecting the strongest behavior from each model.

The most important lesson was that, for this competition, improving the deterministic teacher was more valuable than changing SFT hyperparameters.

Brief summary

The key elements of our 2nd public / 6th private solutions were:

Validation strategy.

Bit-manipulation and cryparithemtic algorithmic solvers.

Training on a massive synthetic dataset.

Overall summary and a training routine

We started to build our work on a @huikang OPP write-up. It was well aligned with our initial understanding of the problem and provided a great baseline with good algorithmic solvers.

Most of our hypotheses were tested using Unsloth in Kaggle/Google Cloud G4 enviroments. Our standard setup used a 32 BS, 3.5e-4 LR, 32 lora_rank, 32 lora_alpha and 1 epoch. In order to train the adapters much faster in the late stages, we used Tinker.

1. Validation scheme

Most of the public validation strategies were quite simple — a 10% holdout set consisting of 950 samples was used. However, this is not reliable enough, since even some of the training samples are not learned well with LoRA adapters. Therefore, we decided to use the full training data as validation, effectively increasing the validation set size by x10. In order to do so, we had to create synthetic problems that match the training distribution (see synthetic data section below).

Per domain public checks aka LB probing

Considering the inference time, the public score distribution, and a common sense, it was natural to assume that the test set consisted of 500 problems split 250/250 between public/private. From that we basically understood that each 0.01 on the LB corresponded to 3 solved problems. So we used -0, -1, -2 notation for our submission scores to track progress more easily.

250/250 problems is a small sample and the train distirbution could have been skewed a bit between public/private. Moreover, making changes to a single domain CoTs could negatively affect the other domains. That's why it was important to understand per-domain quality of the algorithmic solver / other improvements. We came up with the following procedure:

For the selected domain, we used algorithmic CoTs.

For all other domains, we trained the model to output I will ignore this problem\n\boxed{DUMMY} for the input prompt.

This allowed us to retrieve a pure per-domain signal from the public LB. Below are the results for some bit-manipulation solver tests when using 5k (OPP algorithm) vs 12.6k (ours algorithm) training samples:

Skips. For example, for (shl(x, a) XOR NOT rotr(x, b)) OR shr(x, c) we can skip iteration over c if (shl(x, a) XOR NOT rotr(x, b)) is less than result (same for AND since both are monotonic).

add: a + b sub: a - b mul: a * b max_mod_min: max(a, b) % min(a, b)
add_p1: a + b + 1 sub_ba: b - a mul_p1: a * b + 1
add_m1: a + b - 1 abs_diff: |a - b| mul_m1: a * b - 1
 neg_abs_diff: -|a - b|

The algorithm is a depth-first tree search, where depth is a number of fully mapped equations:

Start with an empty mapping

Pick a new equation

Start / continue the search over all unmapped symbols (both digits and operation)

As soon as symbols are mapped into a correct equation, go to 2

If no correct mapping is found for current equation, abandon last accepted equation and go to 3.

If all equations are mapped, try to calculate the answer

Additionally, we check the possibility of all numbers being inverted. If forward search fails, we start anew the reversed search. Approximately 40% of solved problems are solved in reversed mode.

A representative example of our reasoning trace can be found in the attachments (or here).

Results

Our best version solves 240 / 654 cryptarithm_deduce problems from train.csv under limit after training on ~100M tokens.

We also finalized a ligher version that solves 170 problems under limit and poses less threat to other categories. We used this algorithm for the final selected submission (more on that later).

Optimizations

Operation deduction. Before the search, we restrict each operation symbol usually 2-3 possible operations based on result lengths, whether result is positive or negative, and the fact that no more than one operation from each family can be in a problem.

Leading zero. For first digits in operands and results, we remove zero from the set of possible digits.

Leading one. If possible mappings for an operation is reduced to add family only and result is three-digit, we auto deduce the first digit to be 1.

Equation sorting. First, we search equations with as few unique unknown digits as possible.

Equation numeric solver

Same as cryptarithm, but much easier since all digits are known. Solves 550 / 594 equation_numeric_guess problems from train.csv.

3. Synthetic data

Since our validation scheme did not allow us to use the training data to obtain clean metrics, we focused on creating a synthetic dataset instead.

3.1. Cipher, gravity, unit conversion

To create synthetic data matching the training distribution, we used the distribution of the number of examples per prompt for all domains. In addition, for each domain specifically, we considered the following:

Gravity and unit conversion: calculated empirical distribution of example parameters, query parameters, answers. Then, we simply sampled numbers from these distributions.

Ciphers: number of unseen characters, words distribution, sentence structure. 

During validation, we found several problematic patterns for our adapters. For example, the following hallucinations occurred quite often:

*LoRA adapter output*

s-t-u-d-e-n-t->「sent」

*LoRA adapter output*

c-l-e-v-e-r->「letter」

To directly mitigate this issue, we created a targeted subset focused on these and other common failure cases. Adding that subset solved that issue.

One more common failure pattern was a repeatness. We are sure that it is poissble to mitigate this by choosing another algorithmiс solver, but we didn't have time to find a proper one.

3.2. Bit manipulation

For each formula template, we generate samples with different shift values, number of equations and inputs. For training, we increased rate of complex three-atom problems to learn them better.

3.3. Cryparithmetic, equation numeric

We collected stats from train.csv on the number of equations, unique digits, unique operations, reversals, etc. Our cryptarithm synthetic generator fixes key properties of a problem (set of operation, reversal) and keeps rerolling digit mappings until the reasoner solves this problem correctly under token limit.

We built a new generator and synthesized many similar problems

Although the reasoner could correctly solve 87.8% of the problems, the best public notebook score remained at 0.86. We suspected that the gap was caused by a shortage of training data.

Therefore, we extracted various task-level statistics from train.csv and built a program that could generate an arbitrary number of rule_found samples.

The statistics we used included character frequencies, numeric ranges and distributions, and distributions of transformation methods.

To improve the quality of the generator, we trained the model only on synthetic data and evaluated it on both synthetic data and original data. If the synthetic data perfectly imitated the original data, the evaluation accuracy on synthetic data and original data should be the same. By measuring this gap, we identified missing factors in the synthetic data generation algorithm and iteratively fixed them.

In the final submission, we trained with a ratio of "synthetic data : original data = 2.5 : 1", using synthetic data first and then original data.

Longer training improved the loss, especially on difficult tasks.

Tokenization trick (synthetic tokens for cryptarithm)

In cryptarithm tasks, tokenizer segmentation sometimes caused multiple characters to be handled as a single token. This issue was also discussed in the competition discussions.

To address this, we used synthetic tokens that force each single character to be encoded as one token, making the learning process more stable.

Additional Improvements

Gradient clipping

In the public notebook, the gradient clipping value was set extremely high at 1e9.

We found that this was causing training instability, so we clipped gradients at 1.5.

There were discussions about scores varying from submission to submission, and we believe this may have been one of the causes.

The figure below shows an example where the same training setup produced very different LB scores depending on whether gradient explosion occurred.

[图 4: inbox%2F20464683%2F30a272f565e44f6723a0dd7898ec75c1%2FIMG_1905.PNG]

Local validation strategy

Until the middle of the competition, we validated by training on synthetic data and evaluating on original data. For submissions, we trained on both synthetic data and original data.

However, as we improved the quality of the generator, the model became increasingly overfit to the original data, and we observed a divergence between local validation and Public LB.

Therefore, for the final stage, we decided to prioritize Public LB, which was based on unseen data, over local validation.

What Did Not Work

Generating CoTs with higher temperature and applying reinforcement learning (SimPO / ORPO)

When we inspected model failures, we found that in many cases the model produced CoTs that were very close to the correct ones. Therefore, we thought that instead of only increasing the probability of correct outputs through SFT, we also needed to reduce the probability of failures through reinforcement learning.

To create failed examples (rejected), we sampled from the SFT model with temperature set to 1.3.

For chosen, we used the output of the reasoner as is.

We performed preference learning with SimPO / ORPO using these output pairs. However, it did not improve accuracy as much as expected, so we did not use it in the final submission.

In the training logs, we observed some cases where the probability of the chosen side increased, but we saw almost no decrease in the probability of the rejected side, which was what we had expected.

We believe that learning did not progress sufficiently because chosen and rejected were too similar.

[图 5: inbox%2F20464683%2F20601595763e31a891259704732596cc%2FIMG_1906.PNG]

Solving new problems

For us, solving bit_manipulation and cryptarithm tasks and creating CoTs that an LLM could imitate was very difficult.

Algorithms that solve these problems with high accuracy require a large amount of search, and it was very difficult for an LLM to imitate them within a limited token budget.

We also used Claude Fable 5, but we were not able to develop a sufficiently strong reasoner.

### 7th Place Solution: Solving Bitmanipulation via String Matching and Backtracking

来源：https://www.kaggle.com/competitions/nvidia-nemotron-model-reasoning-challenge/discussion/712395

First and foremost, we would like to thank the organizers (NVIDIA and kaggle) for hosting this incredibly challenging and unique competition. Congratulations to all the winners! 

While we competed across all tasks, our primary algorithmic and ML innovations focused heavily on the Bit Manipulation Puzzles, achieving >96% validation accuracy (we expect it to reach >98% with more training steps) —representing the highest performance in this category by any participating team.

To solve this, we abandoned arithmetic logic entirely. Here are the main innovations of our approach:

Bases and Truth Table Formulation: We reframed logic-gate deduction into a discrete feature-selection task. By leveraging string similarity (minimal bit flips) between outputs, we isolated primitive transformations ("bases") and deduced their truth tables without any complex arithmetic.

Backtracking and Error Recovery: We formalized a structured search process that tests candidate bases, detects logical collisions across a 64-row puzzle dataset, and deterministically backtracks upon failure to perform robust error recovery.

Bit Tokenization and Interactive Reasoning SFT: We bypassed standard tokenization to force the model to encode binary strings as individual, single-bit tokens (avoiding arbitrary chunking like 10100011 to [1010], [00], and [11]). Then, using Dynamic Loss Masking—training the model to natively hypothesize, self-evaluate, and backtrack.
