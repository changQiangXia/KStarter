### 3rd Place Solution — OOF Stacking + AutoGluon

来源：https://www.kaggle.com/competitions/playground-series-s5e8/discussion/603198

Many thanks to Kaggle for organizing such a wonderful Playground competition! This month’s dataset was excellent, and I truly enjoyed the process and learned a lot. 

Special thanks to @mulicmu ’s “Dive into Deep Learning”, the AutoGluon library, @optimistix for the ideas shared in the 1st place solution, @cdeotte for his enthusiastic sharing, and to everyone in the community who openly shared their work and ideas.

📌 Solution Approach

My main idea was to use iterative OOF stacking combined with AutoGluon. The workflow was as follows:

Collect OOF and submission files: Gather OOF predictions and submissions from high-quality notebooks and my own models, while filtering out those with leakage or inflated CV scores.

Train with AutoGluon: Use the selected OOF files as features for AutoGluon, train new models, and generate fresh OOF and submission files while recording feature importance.

Filter features: Analyze feature importance and select high-quality features for the next round.

Iterate the process: Repeat steps 1–3, continually adding new models and OOFs to steadily improve ensemble performance.

📌 Feature Engineering Summary

Based on the raw data, I designed and constructed around 30 new features from duration, balance, age, month, and day, mainly including:

Nonlinear transformations: log, sqrt, square, cube, and exponential transformations.

Binning features: quantile-based binning (5/10/20/30 bins) to generate categorical-like features.

Statistical features: indicators for long/very long duration, absolute balance and squared terms.

Ratio features: duration-to-campaign ratio, balance-to-duration ratio.

Cyclical features: sine and cosine encodings for the day variable.

Seasonal features: indicator for peak business months (March, April, May, September, October, November).

Overall Conclusion

Feature Interactions

Pairwise combinations (length = 2): Provided consistent and noticeable improvements, the most effective interaction strategy so far.

Triple combinations (length = 3): Tried, but gains were minimal and sometimes introduced noise, leading to limited benefit.

Target / Categorical Encoding (TE & CE)

Very effective, among the most impactful techniques for performance improvement.

Manually Engineered Features

Added some value, but overall impact was weaker compared to feature interactions and TE/CE.

For single models, increasing the number of cross-validation folds often helps improve performance, though too many folds can be counterproductive.

Best path forward: Focus on strong pairwise interactions, then integrate TE/CE.

Other engineered features can serve as complementary additions but are not the main drivers of performance.

This may be partly explained by the nature of Kaggle Playground datasets, which are synthetically generated. In such data, handcrafted feature engineering often has limited effectiveness compared to systematic interactions and encoding methods.

### XGBoost - QuantileDMatrix Trick

来源：https://www.kaggle.com/competitions/playground-series-s5e8/discussion/600048

I would like to share an XGBoost trick to handle larger data and more features. When we use the Python API, we create a xgb.DMatrix() to wrap our data before train and predict. If we use an xgb.QuantileDMatrix() instead, then we can train with up to 8x more data!

XGBoost uses Histogram

The most common tree_method is hist. This takes each column of numbers (whether int64, int32, float64, or float32, etc) and puts it into 256 bins for training and inference (when we use the default value for max_bins). This means that the original column of 8 bytes or 4 bytes per number becomes 1 byte per number!

So when our train data is 32bit precision, it gets reduced by 4x when XGB is training. (Or if it is originally 64bit precision, it gets reduced by 8x). This is good news because this means we can train with larger dataframes than we think when using XGB.

Use QuantileDMatrix (Trick 1)

Let's look at an example. Imagine that we have a dataframe with 1 million rows and 1000 columns. This is 1e9 elements (i.e. numbers). If each number is 32bit precision (i.e. 4 bytes), then this dataframe is 4GB of data. When we use xgb.DMatix(), this entire 4GB first gets loaded into GPU VRAM before it gets compressed into histograms and finishes as 1GB of data.

When we use xgb.QuantileDMatrix(), then the data gets loaded into memory in batches. First we load 1GB and it gets compressed to 250MB. Then we load another 1GB and it gets compressed to 250MB, etc etc. So the xgbQuantileDMatrix() doesn't require us to have 4GB of GPU VRAM if we wish to train on a 4GB dataframe. Also, we choose the size of the batches, so if we make them small, then we only need about 1GB of GPU VRAM to train with 4GB of 32bit dataframe.

Reduce Data Types (Trick 2)

By default, Pandas and NVIDIA cuDF loads numbers as int64 and float64. Usually this is more than we need. We can nearly always reduce integers to int32 and float32. Doing this reduces our data by a factor of 2x. So first, we should read and reduce our data. And second, we can use xgb.QuantileDMatrix(). The combination of both of these techniques allows us to train with up to 8x more data!

Maximize QuantileDMatrix with Disk (Trick 3)

To maximize the benefit of xgb.QuantileDMatrix(), we can use two notebooks. In the first notebook we perform GPU (i.e. NVIDIA cuDF) feature engineering and save the dataframe to disk. In the second notebook we design our data loader to read batches from disk.

The reason this maximizes the size of data we can train with is as follows. Imagine that we have a 15GB dataframe and 16GB of GPU VRAM. If we use NVIDIA cuDF to build our dataframe, then we are already using 15GB of GPU VRAM (to store our original dataframe) when we begin to build our xgb.QuantileDMatrix(), so we only have 1GB left over to fit the XGB train data.

If we build our 15GB GPU dataframe in one notebook and save to disk. Then our second notebook begins with all of its GPU VRAM available. Then inside our data loader which feeds our xgb.QuantileDMatrix(), we read 16k rows of our dataframe at a time, transfer it into GPU VRAM and compress it to 4x smaller size. In the end XGB will only use 15/4 = 3.75GB of our 16GB GPU VRAM. And the original 15GB dataframe is not anywhere in our notebook's memory. It only exists on disk.

### Are We Here to Learn or Just to Ensemble Submissions?

来源：https://www.kaggle.com/competitions/playground-series-s5e8/discussion/596589

Why do so few participants choose to build models from scratch, try different modeling techniques, and seriously explore feature engineering?

Since the competition started, I've seen dozens of notebooks chasing tiny leaderboard gains through ensembles. Same public submission files, stacked, blended, voted again and again… How many people have actually won a competition using only this approach?

Let’s be real: in the real world, nobody hands you five .csv files and says, “Just ensemble these and deploy.” That world doesn’t exist. What does exist is starting from raw data, building features, testing hypotheses, and creating robust models from the ground up.

Leaderboard engineering might give a short-term dopamine hit, but what does nudging your public score by 0.001 really teach you? Isn't Kaggle supposed to be a platform for learning and practical experimentation? Or is it all just for show now?

How many discussions have you seen that seriously explore the data? That share real, original approaches to modeling or feature pipelines? Not many.

If we're here to grow as practitioners, why are we mostly just ensemble-ing the same few public submissions? Stacking without understanding the data gives a false sense of progress. It's a leaderboard illusion.

Maybe it’s time to ask:

Are we here to learn, to build, or just to show off?
