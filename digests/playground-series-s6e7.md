### [4th Place] From #414 to #4: Trusting OOF When the Leaderboard Lied

来源：https://www.kaggle.com/competitions/playground-series-s6e7/discussion/732487

Hi everyone! First, congratulations to all participants, and thank you to Kaggle and the community for another fun Playground competition.

My final submission scored 0.95094 on the public leaderboard (rank 414) and 0.95084 on the private leaderboard (rank 4 out of 3,356 teams). The score changed by only -0.00010, but the rank improved by 410 places.

That shake-up is the main reason I wanted to write this. The final solution was not a huge stack or an exotic feature factory. It was one FT-Transformer family, one useful representation trick, one metric-aware decision rule, and—most importantly—the decision to trust honest out-of-fold validation over a crowded public leaderboard.

TL;DR

Model: FT-Transformer, 7 folds, with 4 independently initialized members inside each fold.

Features: 13 raw features + 39 multiclass exact-value target-encoding features.

CV: 7-fold stratified CV with every target-derived feature fitted inside the training fold.

Biggest gain: changing the final decision from argmax(p) to argmax(p / class_prior) improved OOF balanced accuracy from 0.89187 to 0.95063.

Final result: Public #414 → Private #4.

Main lesson: align your decision rule with the metric, then trust clean OOF more than tiny public-LB differences.

1. The problem in one minute

We had 690,088 training rows, 295,753 test rows, 13 features, and three target classes:

Class
Training share

at-risk
85.87%

fit
5.77%

unhealthy
8.36%

The metric was balanced accuracy, which is simply the average recall across the three classes.

This matters because ordinary accuracy and balanced accuracy want different things. A model can achieve high ordinary accuracy by favoring the 86% majority class, while balanced accuracy gives the small fit class exactly the same importance as at-risk.

2. Final pipeline

official train/test
 ↓
7-fold StratifiedKFold (shuffle=True, seed=42)
 ↓
fold-local exact-value target encoding
13 raw features + 13 × 3 TE features
 ↓
FT-Transformer × 4 internal members per fold
 ↓
OOF probabilities + fold-averaged test probabilities
 ↓
prior-corrected decision: argmax(probability / class_prior)
 ↓
final labels

There was no cross-model stacking in the final submission. XGBoost, HistGradientBoosting, RealMLP, and kNN-density experiments were useful for checking ideas, but none replaced the FT-Transformer submission.

3. The biggest improvement was not the model

The neural network was trained with ordinary multiclass loss and no class weights. Its raw probabilities therefore reflected the heavily imbalanced training distribution. A normal argmax strongly preferred at-risk.

For balanced accuracy, I used this decision rule:

$$
\hat{y}(x) = \arg\max_k \frac{p(y=k\mid x)}{\pi_k}
$$

Here, $\pi_k$ is the training prior of class $k$. Dividing by the priors asks a simple question: which class would be most likely if all classes were equally common? That is much closer to what balanced accuracy rewards.

The code is tiny:

classes = np.array(["at-risk", "fit", "unhealthy"])
prior = y.value_counts(normalize=True).reindex(classes).to_numpy()

pred = classes[(probabilities / prior).argmax(axis=1)]

This single rule changed 18,151 test predictions, or 6.14% of the test set.

The general lesson is bigger than this competition: probability estimation and the final hard-label decision are separate problems. Before tuning another model parameter, derive what your evaluation metric actually wants.

One warning: class-weighted training and prior correction solve a similar problem. Applying both without checking can over-correct the minority classes.

4. Why exact-value target encoding helped

The second useful idea was to target-encode not only categorical columns, but also the seven numeric columns by their exact values.

That sounds strange. We usually think of numbers as continuous. However, many values in this synthetic dataset were repeated: the generator appeared to resample from a finite support instead of adding fresh continuous noise. A numeric value could therefore behave like a high-cardinality category.

For every one of the 13 input columns and every one of the three classes, the pipeline added the estimated conditional class probability for that exact value:

13 columns × 3 classes = 39 additional features

For example, a repeated step_count value received three features describing how often rows with that value belonged to at-risk, fit, and unhealthy—using training-fold rows only.

Leakage control is essential here:

The encoder for each outer fold was fitted only on that fold's training rows.

Training-fold encodings were themselves generated out of fold.

Validation and test rows only used mappings learned from the training fold.

Without this separation, target encoding can produce a beautiful CV score that disappears immediately on the leaderboard.

There was another useful lesson: this feature looked about -0.0017 on a small 70k-row screen, but about +0.0012 on the full dataset in the original paired experiment. High-cardinality statistics need enough repeated observations. If you want to make that experiment cheaper, reduce folds or epochs—do not remove the rows that allow the signal to exist.

I later checked the same idea with XGBoost and saw the same direction:

That independent result gave me more confidence that the gain came from the data representation, not from one neural architecture getting lucky.

I used fixed epochs instead of selecting the best checkpoint on the same fold later used for scoring. This keeps the outer validation fold as an honest measurement rather than quietly using it for model selection.

The seven corrected fold scores ranged from 0.94812 to 0.95295, so the final OOF score was not carried by one lucky split.

6. What did not make the final solution

A short list of dead ends is often more useful than another parameter table:

Full PLR instead of PLR-lite: about +0.00003, effectively noise.

Small-sample screening for exact-value TE: misleading because the per-value statistics were too sparse.

Adding medium-resolution numeric TE on top of exact TE: -0.00004; no extra signal.

kNN density features: +0.00014; positive, but below my minimum effect threshold.

RealMLP with exact-value TE: strong OOF at 0.95051, but still below the FT-Transformer. Its public/private scores were 0.95062/0.95027.

More complicated blending: no clean OOF evidence that it beat the simple incumbent.

My mistake was spending too much time deeply auditing several tiny ideas after a strong candidate already existed. Next time I would use a two-stage process: cheap, leakage-safe screening for every idea, then full reproducibility work only for the best one or two finalists.

7. Public #414, Private #4

The final submission had an OOF score of 0.95063 and a public score of 0.95094, so there was no alarming CV/LB mismatch. But the public leaderboard was extremely dense, and that score was only rank 414.

It was tempting to interpret this as evidence that the solution was not competitive. I did not replace it, because:

the validation pipeline was leakage-safe;

the gain had a clear mechanism;

per-class recall was stable;

all seven folds were reasonable;

later candidates did not beat it honestly.

The private score was 0.95084, almost unchanged from public, but it became the official fourth-place result. Kaggle displays five decimals, and places 3–8 all display 0.95084, so I cannot say anything about the hidden precision behind that ordering. I can only happily accept the official #4. 😄

The public leaderboard was useful as a smoke test: it confirmed that the file format, label mapping, and broad validation story were sane. It was not precise enough to select among models separated by a few ten-thousandths.

8. Credit and reproducibility

The final FT-Transformer implementation, training recipe, and original OOF/test probability files came from Masaya Kawamata's public notebook. Full credit to Masaya for sharing a very strong solution with the community.

My contribution was to treat it as a candidate rather than a black box: I audited the fold-local target encoding, recomputed the metric and prior correction, checked fold and class stability, reconstructed the final CSV from the saved probabilities, and compared it against independently trained alternatives. The reconstructed labels matched the submitted file exactly.

I think public notebooks are one of Kaggle's best learning resources. Using one is easy; understanding why it works, checking that it is honest, and knowing when to trust it are the parts that transfer to the next competition.

Final takeaways

If I had to keep only four lessons from this competition, they would be:

Align the decision rule with the metric. The largest gain may happen after predict_proba.

Study the data generator. Repeated “numeric” values can contain categorical-style signal in synthetic tabular data.

Match cheap experiments to the idea. High-cardinality statistics need the full sample size.

Trust honest OOF over leaderboard noise. Public rank is a useful warning light, not always a useful steering wheel.

Thanks for reading, and congratulations again to everyone! I am happy to discuss any part of the validation, target encoding, or prior correction in the comments. If this saves you from one misleading public-LB chase or one badly screened TE experiment, an upvote would make my day. 😄

### 2nd Place Solution: Trusting CV & Mathematical Precision

来源：https://www.kaggle.com/competitions/playground-series-s6e7/discussion/731904

Here is the writeup of our 2nd place solution, focusing on a robust two-step optimization pipeline applied across 18 base predictors.

Key Highlights & Performance

Ensemble Scale: Integrated 18 base predictors (including diverse implementations of LightGBM, XGBoost, CatBoost, FT-Transformer, RealMLP, and HGBC).

LogLoss Optimization: Reduced OOF LogLoss from 0.105495 (Equal Weight Baseline) down to 0.086310.

Balanced Accuracy Boost: Achieved an OOF Balanced Accuracy of 0.950737 (a +0.061605 improvement over raw argmax).

Methodological Pipeline

1. Simplex-Constrained Multi-Class Weight Optimization (SLSQP)

Instead of a standard uniform average, we optimized class-specific weights $W \in \mathbb{R}^{18 \times 3}$ across all 18 base predictors (54 parameters in total) using SLSQP.

Objective & Constraint: Directly minimize OOF LogLoss. Weights are normalized per class inside the objective function, effectively enforcing a simplex constraint (\sum_m w_{m, c} = 1).

Renormalization: The blended class scores are finally renormalized to form valid probability distributions before evaluating LogLoss.

Complementary Strengths: The optimized weights indicate complementary predictive strengths among the base predictors:

ftt_kawamata (FT-Transformer) received the largest optimized weight across all three classes, contributing 71.81% for Class 0, 62.45% for Class 1, and 50.28% for Class 2.

xgb_ovr_kawamata (XGBoost OvR) acts as a strong complementary predictor, accounting for 45.59% in Class 2 and 28.19% in Class 1.

2. Direct Linear Blending

Rather than training an additional nonlinear meta-learning stage (which risks overfitting out-of-fold metadata), we used a direct linear combination of the base predictions, preserving the linear interpretability of the ensemble weights.

3. Metric-Specific Multiplier Tuning (Nelder-Mead)

To address class imbalance and maximize the target evaluation metric (Balanced Accuracy), we tuned class-wise probability multipliers on the full OOF predictions using Nelder-Mead:

Optimized Multipliers: [C_0: 0.124044, \quad C_1: 1.499826, \quad C_2: 1.250181]

Test Application: These multipliers were optimized on the full OOF predictions and then applied unchanged to the test set predictions. No test labels or leaderboard feedback were used for tuning.

Impact: Down-weighting Class 0 while boosting minority classes (Class 1 and Class 2) improved Balanced Accuracy from 0.889132 (raw argmax) to 0.950737.

### 29th Place Solution: FT-Transformer + Exact-Value Target Encoding 

来源：https://www.kaggle.com/competitions/playground-series-s6e7/discussion/732394

29th Place: FT-Transformer + Exact-Value Target Encoding, and a +643-place case for trusting your CV

TL;DR — Public 0.95034 (rank ~672) → Private 0.95070 (29th / 3,356). No public-LB
chasing: both final submissions were chosen weeks in advance by nested cross-validation, and in
hindsight the CV pick was our best private score out of all 14 submissions. The model that did it
is a single FT-Transformer with fold-local exact-value target encoding — plus a long list of
things that did NOT work, which I think is the more useful half of this post.

The public board had v35 at ~rank 672. The private board put it 29th. The gap between our public
and private ranks was not luck: with fit = 39.8k and unhealthy = 57.7k rows out of 690k,
public-LB movement of ±0.001–0.002 is binomial noise on the minority classes. Masaya Kawamata's
"Trust your CV" thread made that case quantitatively mid-competition, and it was the compass for
our endgame — we stopped submitting entirely two weeks before the deadline once CV said nothing
more was left.

The model (v35)

A clean reproduction of @masayakawamata's FT-Transformer-v2 recipe, rebuilt from the notebook's
code rather than its artifacts (all credit for the architecture to him — his own paired ablation
showed the gain comes from the encoding, +0.0012, not from the transformer itself, +0.00003):

Exact-value target encoding of all 13 columns — every distinct numeric value gets its own
target statistic. The health-risk data is quantized enough that exact values carry signal that
binned or smoothed TEs blur away.

Fitted inside every outer training fold — the TE tables never see the fold they encode.
This is the difference between a real 0.9507 and a leaky 0.96 that collapses on private.

Single ensemble member (n_ens=1): four members cost 4x GPU time for noise-level gains.

Fixed 16-epoch budget, no early stopping, PLR-lite numeric embeddings, prior-correction of the
predicted class distribution.

What did NOT work (32 falsified levers, the honest ledger)

Everything below was implemented, cross-validated with the same nested protocol, and rejected —
posting these so you don't have to rediscover them:

TabPFN v2 as an ensemble leg — error correlation 0.914 with the GBDT legs (we expected
~0.2 from a "different prior"); the stacker assigned it zero weight. Foundation-model
diversity was an illusion here.

Row-segment specialists (e.g. a dedicated model for rows with missing sleep features) —
no segment ever beat the global model on its own segment.

Corrected-KNN density features — public 0.94987, worse than either final.

Greedy hill-climb over all saved legs — converged back to v31's weights; ensembling was
saturated months of levers ago.

Ratio/product feature engineering — duplicated what the exact-value TEs already encode.

Class-multiplier micro-search beyond a simple prior^beta correction — pure CV noise.

The meta-lesson we took from a previous Playground (s6e6, where a public-anchor final cost us
~335 private ranks): the public LB is a small-sample estimate dominated by minority-class noise,
and every point of contact you give it corrupts your selection. This time the discipline paid.

The gap to the top, quantified

2nd place (0.95085, +0.00015 over us — congrats @kava1, great writeup) used the same best base
family (Kawamata's FTT), but blended 18 diverse base predictors with class-specific simplex
weights (an 18×3 weight matrix optimized by SLSQP on smooth OOF LogLoss, then Nelder-Mead class
multipliers for balanced accuracy). His ensemble's OOF (0.950737) beat our v31's (0.950579) by
almost exactly his private margin. The lesson repeats across Playgrounds: past a strong single
model, the remaining edge is breadth of genuinely diverse bases — not deeper ensembling of one
lineage (which is exactly the lever our hill-climb correctly reported as empty).

One practical GPU note

Kaggle still assigns P100s (sm_60), and the preinstalled PyTorch wheel has no sm_60 kernels —
your first CUDA op dies with no kernel image is available. The notebook detects the GPU and
conditionally installs the cu126 wheel on P100 only (never blind-reinstall torch — the
torchvision/numpy cascade is worse than the disease). Pinning the T4 via kernel metadata
("machine_shape": "NvidiaTeslaT4") avoids the issue entirely for API pushes.

Training notebook (full reproduction, runs end-to-end on Kaggle GPU): https://www.kaggle.com/code/satyapb2002/29th-place-ftt-exact-value-target-encoding

Thanks to @masayakawamata for the architecture and the CV-trust analysis, @kava1 for the 2nd-place
writeup, and everyone who shared baselines. Questions welcome — happy to share any of the
falsified-lever details.

### 135th Place Solution - My First Full Competition

来源：https://www.kaggle.com/competitions/playground-series-s6e7/discussion/731907

My goal was to work through a proper tabular machine learning workflow: EDA, validation, feature engineering, individual models, OOF predictions, and blending.
My EDA did not lead to one single breakthrough, but it helped me understand the class imbalance, missingness patterns (train and test were extremely similar), strongest variables, and the repeated-value structure that later made target encoding useful.

The improvement over the best single model was small, so I tried to be careful not to overfit the public leaderboard.

What worked

The most important things for me were:

saving OOF and test probabilities for every serious model

using balanced accuracy and class-wise recall rather than ordinary accuracy

target encoding repeated numerical values

prior correction for LightGBM probabilities

blending only models that added useful diversity

What did not work as well

A few things were useful to try but did not make the final solution stronger:

Random Forest performed well but did not improve the final blend

a basic neural network was weaker than tree-based models and RealMLP

logistic regression stacking did not beat simple probability blending

adding every model to the blend was worse than using the strongest four

a simple rule-based model captured some signal but was much weaker than the learned models

What I learned

This competition helped me understand why OOF predictions are so important. Before this, I understood cross-validation in theory, but this was the first time I properly used OOF predictions for model comparison and blending.

Overall, this was a very useful first full Kaggle workflow for me. Now to learn from the top solutions. One useful idea from @kava1 's 2nd place writeup was to try class-specific blend weights, since different models may be better at predicting different classes.

### Plausible generation model of the "original" dataset

来源：https://www.kaggle.com/competitions/playground-series-s6e7/discussion/717222

The "original" dataset has many features, but it appears that only 3 were useful in generating the target. These are sleep_duration, stress_level and physical_activity_level. With the ground truth being hard labels, it would not be possible to reverse engineer the generation model with certainty because many models would give the same hard labels. One can easily make up such a model:

from sklearn.metrics import balanced_accuracy_score

original = pd.read_csv('/kaggle/input/datasets/ziya07/college-student-health-behavior-dataset/student_health_dataset_50k.csv')
y = original.pop('health_condition')
z = (
 (original.sleep_duration<6).astype(int)*2+
 (original.stress_level=='medium').astype(int)+
 (original.stress_level=='high').astype(int)*3+
 (original.physical_activity_level=='moderate').astype(int)+
 (original.physical_activity_level=='sedentary').astype(int)
)
y_pred = pd.cut(z, [-np.inf, 0, 4, np.inf], labels=['fit', 'at-risk', 'unhealthy']).astype('object')
print(balanced_accuracy_score(y, y_pred))

Is it possible to completely separate the classes with a simple model? I have my doubt. Synthetic datasets are usually created with noise.

Sticking with these 3 features, there are only 18 combinations.

X = pd.DataFrame()
X['sleep_duration<6'] = (original.sleep_duration<6).astype(int)

cols = list(X.columns)

I dont have a lot to talk about this month. I want to share a model pruning experiment I did though. We have 200+ models and generate a prune order according to Optimal Brain Surgery (OBS) on weighted log loss under Logistic Regression. The result shows that we only need about 25 diverse models for optimal performance (this is for Logistic Regression, for tree stackers it prefers to have almost all models, and MLP also prefers 25 models). It also shows that the Balanced Accuracy is extremely noisy. I would say top 100 in this competition is basically a random permutation.
