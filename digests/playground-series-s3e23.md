来源：https://www.kaggle.com/competitions/playground-series-s3e23/discussion/444784

Hi all, 

In this competition the evaluation metric is the popular area under the ROC curve, which is ranking metric. It has shown in previous competitions that this metric can be optimized by the ensemble of different model predictions. This notebook from @ambrosm shows that ensemble works. Then, I decided to use ensemble in a slight different way; that is, I used the hill-climbing strategy that was used in a previous tabular competition by @samuelcortinhas (see this post). The idea behind hill-climbing is very simple. It combines model predictions in a linear fashion as long as the objective metric improves. Notice that in the below implementation of the hill_climbing function, we allow for negative weights. This does not have to be the case all the time. You can restrict the weights to be only positive.

### The McCabe/Halstead Measures - Operators and Operands.

来源：https://www.kaggle.com/competitions/playground-series-s3e23/discussion/444685

McCabe and Halstead features extractors of source code

"Data comes from McCabe and Halstead features extractors of source code. These features were defined in the 70s in an attempt

 to objectively characterize code features that are associated with software quality. The nature of association is under dispute.

"The McCabe and Halstead measures are "module"-based where a "module" is the smallest unit of functionality. In C or Smalltalk,

 "modules" would be called "function" or "method" respectively."

https://www.kaggle.com/datasets/semustafacevik/software-defect-prediction

The Halstead metrics - Operators and Operands

"The Halstead metrics have been with us for a long time. They were designed by Maurice Halstead at a time (1977) when programs were procedural and , in general, monolithic. In other words your average computer program was just one big file of code – probably written in COBOL – whose only sub-division was a procedure or method. This has implications for the use of these metrics with Java code – and we’ll see why later on."

"Halsteads metrics are based on the numbers of operators and operands. This leads us to a set of questions: 

Which Java constructs will we define as operators?

Which Java constructs will we define as operands?

How are the Halstead metrics calculated from these basic counts?

Which parts of the code will we examine to find these operators and operands?

How will we assign the operators and operands to higher level Java constructs – i.e methods, classes, packages?

First we need to decide what we mean by operators and operands. Operators and operands are defined by their relationship to each other – in general an operator carries out an action and an operand participates in such an action. A simple example of an operator is something that carries out an operation using zero or more operands. An operand is something that may participate in an interaction with zero or more operators. 

http://www.virtualmachinery.com/sidebar2.htm

"Halstead complexity measures are software metrics introduced by Maurice Howard Halstead in 1977[1] as part of his treatise on establishing an empirical science of software development. Halstead made the observation that metrics of the software should reflect the implementation or expression of algorithms in different languages, but be independent of their execution on a specific platform. These metrics are therefore computed statically from the code."

"Halstead's goal was to identify measurable properties of software, and the relations between them. This is similar to the identification of measurable properties of matter (like the volume, mass, and pressure of a gas) and the relationships between them (analogous to the gas equation). Thus his metrics are actually not just complexity metrics."

https://en.wikipedia.org/wiki/Halstead_complexity_measures

Halstead Complexity Report

"The Halstead Complexity Report generates software metrics that are computed statically without program execution. Halstead complexity can be used to compare the complexity between two programs or two applications."

"Cyclomatic complexity is a measurement developed by Thomas McCabe to determine the stability and level of confidence in a program. It measures the number of linearly-independent paths through a program module. Programs with lower Cyclomatic complexity are easier to understand and less risky to modify."

"Rational® Asset Analyzer calculates an approximation of Cyclomatic complexity for COBOL and PL/I programs by counting the splitting nodes in a program and adding one. A splitting node is a logic branch point in a program, a point at which one or more paths through the program can be taken according to the outcome of some logical operation. A splitting node is a branch point with more than one path leading to other nodes. A nonsplitting node has just one path leading to another node."

First of all, I would like to start with a big thank you to Kaggle for running this episode of the playground series. In this post, I will briefly explain my approach, which most of it can be found in my notebook.

Pre-processing

Then, I log-transform all of the input features as suggested by @ambrosm in this post. The surprising factor here was that there was a small improvement in model performance in most of the tree-based and boosted-tree models that I considered after the inputs were log-transformed. 

Models & Ensemble

What did not work

I tried a few different things:

Initially I tried PCA as a way to reduce the number of input features to help reduce the model building time. In my notebook, I highlighted that 10 components explain more than 99% of the variability of the data. However, using PCA instead of the log-tranform features did not help with model performance.

I also tried t-SNE to see if there was a way to separate the two classes but it did not help.

I also tried clustering as presented in my notebook. But it failed. I even tried target encoding with the clusters but there no improvement in model performance.

In this comp, ensemble and model diversity were the key to victory!

### Instructions for winning the competition

来源：https://www.kaggle.com/competitions/playground-series-s3e23/discussion/445245

We recently have had playground competitions with huge shakeups. This competition will be different: The dataset is benign and solid work will lead to victory.

The main steps to victory are:

Choose and implement a solid cross-validation strategy

Implement at least the following seven classifiers

RandomForestClassifier

ExtraTreesClassifier

HistGradientBoostingClassifier

XGBClassifier

LGBMClassifier

CatBoostClassifier

one non-tree model (the best one you can find), for instance a kernel approximation classifier

Tune the preprocessing and all hyperparameters of every single classifier for maximum auc score in cross-validation

Implement an ensemble of all these classifiers

Tune the ensemble weights for maximum auc score in cross-validation

Compute the test predictions and submit

Background for step 1 (cross-validation): During the three weeks of this competition, you'll evaluate hundreds of models and hyperparameter settings. Cross-validation is important because (a) cv scores are more precise than scores based on a simple train-test split, (b) cv scores are more precise than leaderboard scores and you need precise data to take the right decisions, and (c) you can't evaluate hundreds of models in 21 days with only 5 submissions per day. You'll most probably use a StratifiedKFold or a RepeatedStratifiedKFold in this competition. If you see a public notebook without cross-validation, ignore it. If you see a public notebook with a low cross-validation score, ignore it.

Background for step 2 (classifiers): Kaggle competitions are usually won by an ensemble of models. The more diverse the ensemble, the better. The seven classifiers on the list have been chosen because they give good scores for the competition dataset. Six of them are based on decision trees, but an ensemble created only from decision trees isn't diverse enough. My current favorite for the the seventh model (the non-tree model) is logistic regression with Nyström kernel approximation. It is the best non-decision-tree model I could find, and it is competitive (see bar chart). Sample code for the kernel approximation is in the EDA which makes sense.

Background for step 3 (preprocessing and hyperparameter tuning): All these classifiers have hyperparameters, and the default settings are never good enough for a Kaggle competition. Read the documentation to understand the hyperparameters. Background for step 5 (ensemble weight tuning): Ensemble weights need to be tuned like every other hyperparameter. And don't tune them for the public leaderboard (although it's tempting), but for cross-validation!

If you follow all steps of these instructions, you'll have a good chance of ending up among the top 10 % of the private leaderboard. And even if you follow only a part of the steps, you'll gain a lot of useful experience.
