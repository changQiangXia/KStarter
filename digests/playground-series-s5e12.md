### [2nd Place] Winning based on ID Shift Analysis 

来源：https://www.kaggle.com/competitions/playground-series-s5e12/discussion/665385

Thanks

Happy New Year! This month-long marathon is finally over! Congratulations to all the winners! I want to thank the organizers for hosting this interesting competition.

This was my first time participating in a Playground Series, and I truly poured my heart and soul into it. I started learning ML and joined Kaggle in March 2025, so it has been 9 months now. This is a wonderful New Year's gift. I hope to share this joy with all Kagglers in the community, and I wish you all the best in 2026!!!

Learning from discussion

Since the start of this competition, I almost never looked at the public notebooks in the code section because it was filled with "upvote bait"—notebooks where people simply mix others' kernels to farm upvotes. Additionally, there were one or more arrogant cheaters using multiple accounts to perform "blind blending."

In contrast, the discussion section contained a lot of high-quality content. I read every single post in the discussions in detail and drew significant inspiration from them:

Orig FE

@masayakawamata shared in this post that using statistical features from the original dataset could lead to score improvements. This indeed increased my score slightly; however, I didn't perform any aggressive Feature Engineering, so I only attempted to use the most fundamental statistics.

The weird dataset

@tilii7 mentioned in this post that this dataset is very strange. The organizers distorted the feature distributions and removed decisive strong features, resulting in an inconsistency between the Train and Test distributions. To be honest, at that point, I even considered giving up on the competition.

ID Shift

The turning point came with this post by @laureanoarcanio . I strongly recommend everyone read this post as it was the pivotal moment of this competition. He mentioned a phenomenon: using id as a feature surprisingly boosts the LB score.

Furthermore, @alan1305 pointed out:

 
One possible reason could be the interaction of id and physical_activity_minutes_per_week. If we plot the rolling mean of physical_activity_minutes_per_week, it shifts to test distribution at the end of train dataset. Therefore, including id may help indicate which row is "closer" to test set.

I conducted an Adversarial Validation analysis (Micro-Scan of the Tail Transition) and found that this phenomenon indeed exists: the closer the data is to the tail, the closer its distribution is to the test set.

This is actually a serious case of ID leakage, but given the significant shift between train and test, this finding was crucial. (I honestly don't know why @alan1305 only received 5 upvotes… This was clearly a game-changing finding, yet people were busy upvoting public blind-blending notebooks…)

A validation strategy

In this post, @masayakawamata proposed a new validation strategy. Since the tail data better "represents" the test set, it makes sense to use the tail data directly for CV. He also introduced sample weighting.

Concept Shift

@siukeitin mentioned in this post that simple sample weighting doesn't work well because there is Concept Shift.

I also conducted experiments regarding this. More specifically, within the training set, the more the data resembles the test set (low covariate shift), the greater the concept shift becomes. I divided the data into 10 bins and found that samples with the smallest covariate shift had the largest discrepancy in label distribution, whereas the original dataset did not suffer from this issue.

Some advice for beginners

I noticed that many participants in this competition appear to be new to machine learning. As a beginner myself, I completely understand the learning curve, so I’d like to share a few simple tips based on my experience:

Conduct purposeful EDA.
The ultimate goal of Exploratory Data Analysis (EDA) is to guide your modeling strategy. If your data analysis doesn't provide insights for feature engineering or model selection—and is just about plotting pretty charts—then I believe it lacks real value. Always ask yourself: "How does this plot help me build a better model?"

Don't obsess over micro-tuning hyperparameters.
Spending too much time fine-tuning parameters is often meaningless. Changing the learning rate from 1e-4 to 1e-5 is rarely worth wasting a submission. The most efficient approach is to spend that time trying out diverse models or exploring new feature engineering ideas.

### From EDA to Baseline: A Hypothesis-Driven Approach (XGBoost + Selective TE)

来源：https://www.kaggle.com/competitions/playground-series-s5e12/discussion/648186

Hello Kagglers,

I believe that steady improvement in competitions comes from a continuous loop of EDA -> Hypothesis -> Experiment. To consistently improve score, maintaining a coherent strategy is essential. I believe EDA is the key to establishing this direction, rather than just blindly tuning parameters.".

I have published a starter notebook that demonstrates one iteration of this loop.

Notebook Link: [https://www.kaggle.com/code/masayakawamata/s5e12-eda-xgb-competition-starter]

The Workflow: From Observation to Implementation

Here is the breakdown of how specific EDA findings led to the modeling strategy in this notebook:

1. Strategy for the Original Dataset

Observation: The distribution of the Original Dataset differs noticeably from the Train/Test datasets (Covariate Shift).

Hypothesis: Concatenating the Original data to the Training set might introduce noise due to the distribution mismatch.

Approach: Instead of concatenation, I adopted the standard practice of using the Original data as an external reference for Feature Engineering. I created statistical features (e.g., Mean/Count encoding based on the Original data) and mapped them to the Train/Test sets to extract underlying signals without altering the training distribution.

reference: [https://www.kaggle.com/code/cdeotte/use-original-data-for-cv-boost-and-lb-boost]

2. Selective Target Encoding

Observation: Many "numerical" features in this dataset actually have very low cardinality (discrete nature). However, some are binary (0/1).

Hypothesis: Tree models might benefit from explicit probability mapping via Target Encoding for these discrete features. However, applying it to binary features is redundant.

Experiment: I implemented Selective Target Encoding, applying it only to numerical columns with nunique > 2, strictly calculated within the Stratified K-Fold loop to prevent leakage.

The Value of Experiment-Driven Approaches

While this notebook prioritizes an EDA-driven hypothesis (avoiding concatenation due to distribution shift), experiment-driven approaches are equally valuable.

Testing Counter-Hypotheses: Even if the distributions differ, simply concatenating the Original data as additional rows might still improve the score depending on the model's robustness. It is definitely worth testing.

Hypothesis from Experiment: sometimes, we find new insights only after running experiments that seem counter-intuitive at first glance.

I discarded the concatenation approach in this specific notebook based on my initial analysis, but I encourage you to challenge this assumption.

Potential Improvements

To further improve accuracy beyond this baseline, the following approaches could be effective:

Interaction Features (High-Cardinality & Target Encoding): Creating pairwise (bigrams) or higher-order combinations of discrete features is a powerful technique. This process intentionally creates high-cardinality features representing specific subgroups (e.g., "AgeGroup_BMI_Gender"). Applying Target Encoding to these specific combinations allows the model to capture fine-grained risk signals that single features cannot represent.

Referencing Past Top Solutions: Since the data structure shares similarities with previous tabular Playground episodes, reviewing and adapting Feature Engineering techniques from top-ranking solutions in the previous competition could provide significant boosts.

https://www.kaggle.com/competitions/playground-series-s5e11/writeups/1st-place-a-lot-of-features-a-lot-of-models-an

https://www.kaggle.com/competitions/playground-series-s5e2/writeups/chris-deotte-1st-place-single-model-feature-engine

https://www.kaggle.com/competitions/playground-series-s5e11/writeups/2nd-place-solution-7-models-but-1-was-also-enou

Implementation Details

Model: XGBoost (Scikit-Learn API)

Validation: 5-Fold Stratified Cross-Validation

Categorical Handling: Factorization + enable_categorical=True

This simple logic, derived directly from looking at the data, provides a stable local CV score. I hope this serves as a good starting point for your own experiments.

### For the (recovering) blind blending addicts

来源：https://www.kaggle.com/competitions/playground-series-s5e12/discussion/651787

We spilled a good deal of virtual ink in the past few months discussing the virtues of proper ensembling, and the reasons not to do blind blending. There are several discussions on that topic that are easy to find, and I will point you to one I wrote a month ago simply to shorten my introduction. The details are in there, but the gist is this: ensembling is fundamental, while blind blending is detrimental!

Yet there are people who do a blind blending of a sort even when they have OOF files and find the blending weights properly. By that I mean that many Kagglers simply throw all the models together and let the hill climbing, logistic regression or ridge decide how much each of those models will contribute. There is nothing wrong with this in principle, as in properly set ensembling pipelines models that bring little diversity should get small or even zero weights. But is there a more predictable way to do this?

I am glad you asked, and the answer is yes. I will again point to a thread that will introduce model diversity and the methodology I use here. In a nutshell, I compare the models by their cumulative distribution functions (CDFs) and use Kolmogorov–Smirnov test to gauge how different two CDFs are. So there is a KS-test number that will tell us how different the two models are (higher KS-test means more divergent), plus there will be two CDF plots for each comparison.

First we do an XGBoost model versus a CatBoost model. They were both trained on identical data - a raw train dataset where numericals and categoricals are treated accordingly - and have similar CV scores (XGB 0.72846, CatB 0.72816). Let's see their CDFs.

[图 1: distributions-Cat-B-XGB.png]

What we look for here is how close those individual lines are to the blue line, which would be a perfect prediction with ~40% zeros and ~60% ones. The models overlap almost perfectly, which is not surprising given the same data and two generally similar model types. If you zoom really close, that green line is in some parts just a bit closer to the blue line, which is to be expected because XGB model has a slightly higher score. The KS-stat is low, which confirms that these two models are not very different. From all of this we can predict that there would be relatively small benefit from ensembling these models, and that turns out to be true.

 
 
 

 

 
 

[ ] [ ]

 

This simple two-model ensemble gives us a 0.00016 boost compared to the best individual model, which is nice.

Let's try a different pair of models. Now we have an XGB model that was trained on an extended train data (target encoding of numerical variables, feature interactions) and has CV: 0.73097. We compare that to a RealMLP model working on a raw train dataset where numericals and categoricals are treated accordingly, but nothing fancy beyond that (CV: 0.72846). Notice two things here: 1) we are matching a GBM and a NN model, which is good; 2) we have a significantly better XGB model, and blind blenders will often tell you that only models of similar scores will blend well.

[图 2: distributions-XGB-Real-MLP.png]

Notice that the two models are clearly separated in this plot: RealMLP is closer to the blue line on the left side, and XGB is closer to the blue line on the right side. In simple terms, RealMLP is better at predicting zeros, while XGB is better at predicting ones. This is exactly what we want: two models that have different strengths, because they will complement each other. Note also that the KS-stat value is much higher than in the first plot, which would lead us to predict that these models will ensemble better. Is that really true?

 
 
 

 

 
 

[ ] [ ]

 

This ensemble produces a 0.00069 boost compared to the XGB model alone. Notice also that a seemingly inferior model got almost a 40% weight. So next time when blind blenders tell you that only models with similar scores blend well, or that model weights should be assigned in proportion to CV scores, please remember that you have a formal proof here that neither one of those statements is necessarily true.

### Kaggle messed up this dataset on purpose

来源：https://www.kaggle.com/competitions/playground-series-s5e12/discussion/652262

We have been at if for a few days, so we have some idea what's happening. Not even sure if I should be writing on this topic so early, as it can potentially dampen the enthusiasm of future users to take part in this competition.

How could that be squared with the lousy models we are making in this competition? Getting AUC of ~0.73 is generally okay, but nothing to write home about. An accuracy value of ~0.69 is not worth bragging about either. In case you haven't checked, our models have log-loss of ~0.58. The best possible log-loss value is 0, and a totally random prediction (a probability of 0.5 for each data point) scores 0.693, so our predictions are much closer to random than perfect. If you still need to visualize how lousy our models are in this competition, here is a cumulative distribution function from one of my other posts. Those lines should be hugging the horizontal blue line at zero in the left part of the plot, and the flat line at 1 in the right part of the plot. Yet they are nowhere near that.

So why are our models so bad if diabetes can generally be predicted well? Part of the answer was given in the post with which I started above: a feature called HbA1c (glycated hemoglobin) has been removed in the dataset we have, even though it is present in original data. More clues can be found here, here and here. All of them boil down to the same thing: there is a significant distribution shift between the original data, which is synthetic to begin with, and our double-synthetic dataset.

I decided to test what kind of a prediction can be made from the original data. I fired up XGB, LGB and CatB with pretty standard parameters, assigned categorical and numerical variables, but other than that didn't do anything else. Their AUC CV scores, in the same order as above: 0.99980, 0.99982 and 0.99989. The original dataset can be classified almost perfectly, and Kaggle decided to muck that up. You will see density distributions below for our data and for the original. In S5E9 we dealt with a dataset to which noise was added deliberately to make it more difficult, and it seems that Inversion and company decided to follow suit. waist_to_hip_ratio was seemingly discretized in our data (by removing or replacing 0.80, 0.90, 1.00, etc values) rather than being continuous. systolic_bp, which was left-side clipped in the original, was made to be narrower and lacks some of the high values. At this point it seems that the original dataset should not be used at all, either by concatenation to train folds, or as a modifier for target encoding.

Kaggle seems to be finding new ways to throw junky data at us, in addition to what @cdeotte uncovered in his famous post. Well done, Kaggle!

### 1st Place Solution | Hill Climbing + Ridge Ensemble

来源：https://www.kaggle.com/competitions/playground-series-s5e12/discussion/665432

Happy New Year, Kaggle Community! 🎉

This win came somewhat unexpectedly, but it validates the sustainability of my favorite Hill Climbing (HC) approach I've been refining over multiple previous competitions, consistently achieving Top 1% places. This was an incredible learning experience, and I want to thank everyone who shared their insights throughout the competition – especially @masayakawamata for the shared post-cutoff cross-validation approach, and @daylighth, @laureanoarcanio, @tilii, @mikhailnaumov, and @siukeitin for their discussion posts and scripts.

This 1st place finish was particularly satisfying because it came after a frustrating plateau. My HC ensemble was stuck at post-cutoff CV 0.7088X and Public LB 0.70722. Any addition of new models caused improvement in CV, but Public LB dropped. I decided to apply Ridge Ensemble Stacking using the top models from HC selection as input. I experimented with different alphas on rank-transformed predictions and different numbers of models. A plateau was achieved here as well, with post-cutoff CV of 0.70860 and Public LB 0.70739. I stopped at this stage as the gap between post-cutoff CV and Public LB of 0.00121 seemed acceptable.

I suppose that the good final result was ensured through leveraging many diverse base models (tree-based and neural networks) with different hyperparameters (depth, learning rate, regularization), feature engineering (ratios, polynomials, target encoding), seeds (multiple runs for variance reduction). I included in HC both single models and other ensembles. Such a mixed approach worked for me in previous competitions.

In the Ridge Ensemble, I focused purely on performance (post-cutoff AUC) rather than correlation-based diversity. The diversity came naturally from HC's exploration process, which tends to select models that complement each other.

The Ridge Ensemble (based on Top-36 models from HC and alpha = 10) had slightly lower post-cutoff CV than HC (0.70860 vs 0.70886), but performed better on both Public and Private LB. This demonstrates that stabilization from Ridge regularization sometimes can be more valuable than raw CV optimization.

With Ridge Ensemble based on Top-34 models and alpha=5, it was possible to achieve a Private LB of 0.70514, but the Public LB score of this ensemble was too low (0.70734) to confidently select it for final submission based on the gap.

Key takeaways in this competition were:
1) distribution shifts are competition killers - if CV improves but LB drops, it is necessary to investigate data structure;

5) always trust your CV and trust the process.

### Suggested roadmap for a beginner for such month-long assignments

来源：https://www.kaggle.com/competitions/playground-series-s5e12/discussion/650676

Hello all,

This post is dedicated to beginners and newcomers to ML and AI who could be looking for a roadmap to approach such assignments. This is a suggestion from my end and one could tailor this to one's needs and time availability, but this could be considered as a base/ blueprint for one's time and effort management in this competition. 

I strongly recommend beginners and newcomers to start early, preferably towards the start of the competition. Starting late will reduce your experimentation time and your final solution may suffer thereby. 

Approach roadmap

Divide your approach into 3-4 steps as below, focusing on effective time management throughout- 

Starting stage - exploration and ideation

This should be done in the first 2-3 days of the competition

Peruse public materials, including shared kernels and discussions

Completely avoid the blind blend kernels and focus on meaningful stuff in the code forums. Focus on kernels that perform EDA and discuss ideas rather than focusing on the score only. 

This will provide sufficient ideas of models that work and don't work on the data and the associated good/ moderate features as well. Focus on the discussion forums for the CV-LB relations and other useful stuff for you to ideate and think through

Single models

Experiment across feature sets, add and remove features based on the CV-score. 

If you are struggling with code writing, use a coding agent like Google antigravity and Claude Code to assist you with the coding endeavor. Iterate through various feature combinations and iterate quickly

Construct meaningful single models and note down the CV scores across individual model options. Number your experiments well and save the out-of-fold predictions and the test set submission files properly

You could submit single models and check the CV-LB relation here - this is important to determine effective and ineffective model options 

Don't delete low performing models until and unless you spot an error - these could be useful additions in an ensemble later

Blend

This is an iterative process again, indulge in cv-backed blending processes every 3-4 days when you have a reasonable amount of single models from your past iterations

Focus on various blending options - a lot of this is discussed in past playground solutions and highly popular posts across the forums 

Build the ensemble using the same CV scheme as the single models for consistency

Submit these blends for your convenience and note down the CV-LB consistency

Try and experiment through the month so that your model pipeline improves consistently 

Final submission choice

Select your final submissions based on the CV-LB score 

We have 2 submission choices - be wise to hedge the risk by selecting diverse model choices - hence experimenting a lot helps 

Document your process and publish it (despite the end result) - this will help you fathom your own process and understand where you need to improve the next month.

Wishing you the best for the assignment and a happy holiday period ahead!

Regards
