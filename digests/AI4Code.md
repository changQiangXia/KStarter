### My understanding of the domain - Taking a step back

来源：https://www.kaggle.com/competitions/AI4Code/discussion/328905

This is a new domain to me. I couldn’t grasp the details of the neat solutions presented and had to take a step back to understand what was going on under-the-hood. I am documenting my findings in case it helps somebody in a position similar to mine. Credit goes to the original authors especially Yuanzhe Zhou and many others who have shared their brilliant ideas.

AN INTERESTING GOAL

The stated goal of this competition is somewhat interesting. The first line states that the goal is to understand the relationship between the code and comment cells. The second line challenges us to reconstruct the order of the markdown cells and this is purely how the winner is measured (the markdowns need to be ordered AND put in the right slots between the code…so the first goal does matter indirectly). We need to rank the markdown cells - identify which comes after the other & put them in he right slot between the appropriate code cells (which are already ordered correctly). The evaluation is based on Kendell Tau - and since folks have already shared some good links explaining the same, we needn’t go deep into the same. It is just an indicator between -1 to +1 on how well the predicted and the actual ranks match.

For a moment, keeping the code part aside, this essentially boils down to ranking a series of texts in the right order. In that sense, it can be reframed as a ranking problem. Now this provides a great relief as there is an extensive body of work under the “Learning to Rank” framework which can now be leveraged. Of course, language models also come into picture. Most of the solutions presented revolve around these 2 items - leveraging language models and leveraging the Learning to Rank framework. We now have a clear sense of direction and can dig into both these aspects and how they help us design a suitable model. But before that - What could be the intent of this competition? This was an interesting question posted https://www.kaggle.com/competitions/AI4Code/discussion/325205 in one of the discussions and my take on it is that this could just be an extension of Google search to cater more efficiently to Code results. We have a query (this is the equivalent of the markdown cell), we have content (this will be the code cell) and what we want is the code cell that is best matched to the query. This is an exciting area. Facebook is doing a lot of work in neural code search, Microsoft has CodeBert and is also neck-deep in the code search domain. Tying natural language to code has immense downstream possibilities. 

Coming to the potential approaches, we have the following:

Rank only the Markdowns without paying heed to the code cells. Use plain NLP for this combined with the LTR (Learning To Rank) frameworks. Surprisingly this seems to get OK results. When given a "context" in the form of code cells these work really well

Tie the Markdown to the code. In this case we dont need to develop a model for ranking because the code cells are already ranked. As long as we are able to match the code to markdown, we directly get the markdown order. 

See how we can leverage both the above approaches.

Learning to Rank framework:

Easiest is to treat this as a regression problem by assigning each markdown cell a score and ranking is obtained by a simple sort. MSE can be the loss function. This is the Pointwise approach. Basically each Markdown cell is scored separately. Though I say regression, we can use Classification, Ordinal regression etc as long as items to be ranked are treated in isolation. This can be further enhanced by providing a "context" in the form of code cells

Then we have the Pair-wise approach: Here we take pairs of 2 markdowns and simply rank which comes first. We now bring relative scores into the picture. This seems cleaner. Cost function typically minimises misclassification of pairwise difference vectors. The challenge is we have too many permutations and combinations while training as well as inference. Moreover, during training we have to identify negative pairs and as of now, there is no great way to decide on what makes a good -ve pair. The interesting part is that in a normal scenario (like in a search query ranking), Pairwise models have a major disadvantage - Every document pair is treated equally important, such setting is not useful in real world scenario because we expect our search systems to answer correctly in top 10 items and not really care about the remaining 11-100 results that much. But in this comp, all the ranks are important and so pair-wise approach becomes much more powerful. 

Then there is the Listwise approach: Idea is to take the whole set and rank every entry in the list at one shot by optimizing ranking metrics directly which is a great thought except that these usually are not continuous and back-prop will not work. So there are interesting proxy approaches to get gradients for these cases to enable us to compute loss and decide the best order.

Lastly, let us look at how the language models can be leveraged:

A plain vanilla approach is to take the query and document (which in our case is the markdown and the code cell), jointly encode the same and fine-tune the model’s classification component to provide a ranking score. Basically tuning is done in such a way that related markdown and code provide better scores compared to unrelated markdown and code. So basically the input to the model is: [ CLS, Markdown text, SEP, code snippet, EOS ]. The vector representation corresponding to the [CLS] token is the one that is used to infer a query-document relevance score. To project the vector of the [CLS] token into a scalar value a single-layer, a fully connected neural network is used which maps from (say) 768 Bert dimensions to one score. If the score is high, it means the markdown and code cells are linked else we check other combinations. In a sense this is like a pair-wise approach except that we are leveraging the language model here

Point-wise approach as discussed above would be to use regression/MSE (or MAE which is better) to rank markdown cells. By giving it a context which contains the code cells this performs really well. So input = md+separator+context

It might be interesting to see if we can bring in list-wise approaches to the language model. See for e.g. https://ai.googleblog.com/2021/07/advances-in-tf-ranking.html. There they learn an independent BERT representation for each  pair, and apply a ranking loss to learn the whole list. But in this competition we just have one mapping ie a markdown cell could map to only one code cell. So there may not be much utility in learning the second best match, 3rd best etc. But can we tweak it in some way such that it takes an ordered code list, an un-ordered markdown list and outputs a sequence list? This has actually been done for plain NLP - see for e.g. https://arxiv.org/pdf/2001.00056v1.pdf but haven't seen any design for bi-modal data.

SRK had suggested the approach of Entailment. Typically, entailment tasks involve a three-way classification of “entailment”, “contradiction”, or “neutral” (i.e., neither). In fact relevance, semantic equivalence, paraphrase, entailment are all similar tasks and with a language model like BERT, looks like the approach may not change much. The standard input template continues to be: [[CLS], s1, [SEP], s2, [SEP]] where s1 and s2 are the two inputs. As long as it is fine-tuned with annotated data that capture the nuances of the target task, the model should be able to figure out how to model the relevant relationship, be it entailment, paraphrase, or query–document relevance.

Code-Aware Language Models

Speaking of language models, this discussion is incomplete without CodeBERT and couple of its more recent peers. CodeBERT is a “bi-modal” pre-trained model where the language model (I think it is same as Roberta) is built using bi-modal data - one being natural language (NL) and the other being Programming Language (PL). The idea is to capture semantic connections between them and produce general purpose representations which can then be used for interesting applications like code-document generation, code search queries etc. In the past bi-modal data has been used in ViLBERT where the two inputs were pairs of language and image and the model learns the implicit alignment between them and predicts whether the caption describes the image content or not. A small difference is that CodeBERT leverages uni-modal data as well as part of training. In other words the inputs are not just pairs of NL/PL as we shall see but also includes raw code which does not have a NL counterpart. Bi-Modal data is processed with standard MLM objective. To process the uni-modal data (ie code without documentation), they use a RTD (replaced token detection objective) which also has side-effect of building generators. So we can generate excellent documentation from the code. The training input is: [ CLS, NLtext 1, NL text2….SEP, code snippet1, code snippet 2… EOS]. CLS is used for classification or ranking. Maybe it is a great delight to have any of the authors of CodeBert participate and share their valuable insights at the end of the competition. Recently, GraphCodeBERT incorporates the data flow extracted from the code structure into CodeBERT.

Most of the time we discussed about converting the 768 dimensions of the CLS vector into a single score. We could also use the same directly to measure cosine distance between them. For e.g. CodeBert is a great unified encoder. We could take a Late Fusion approach as follows - Use CodeBert to encode the Markdown cells and the code cells separately, and then calculate the similarity with a dot-product. In this way, code search is equivalent to find the nearest codes in the shared vector space. In this case, CodeBERT can be fine-tuned with the objective of maximizing the dot-product of the ground truth while minimizing the dot-product of distractors (see eq 15 of the CodeBERT paper for the exact loss). This part is not open-sourced but I guess it may not be too difficult to create it from scratch. 

Around the same time as CodeBERT, we also had the release of CuBERT https://arxiv.org/pdf/2001.00059.pdf. This is trained on Python-only codes (originally, though now maybe other languages are added and originally used only MLM) and may prove to be a neat alternative to CodeBERT as far as this competition is concerned. Unlike CodeBERT, here the inputs i.e the code and comments are not separated with a SEP token but can be mixed freely. The original code is in Tensorflow.

The latest alternative is Salesforce - CodeT5 https://arxiv.org/pdf/2109.00859.pdf which is more recent. In general, I haven't explored T5 series in the past, but I believe these series of models use denoising objectives that corrupt the source input and require the decoder to recover them (MSP - Masked Span Prediction objective). So it is pre-trained with both encoder and decoder pieces thereby giving certain advantages. On top of it they have neat techniques for custom tags in code as well as leverage the tree structure of code well. At the pre-training stage, the model receives either PL-only or NL-PL as inputs depending on whether the code snippet has accompanying NL descriptions or not. For the NL-PL bimodal inputs, they concatenate them into the standard sequence we saw earlier - ([CLS], w1, …, wn, [SEP], c1, …, cm, [SEP]), where n and m denote the number of NL word tokens and PL code tokens, respectively. The NL word sequence will be empty for PL-only unimodal inputs. On top of it they have neat ways to tokenize function names, tree syntax etc. My bets lie with this model

This is an interesting competition and though it needs high end machine to process the whole data, a competitive attempt can be made with just 15-20% of the data and some neat tricks and hacks. All the very best to all the participants.

### 2nd place solution

来源：https://www.kaggle.com/competitions/AI4Code/discussion/343659

The solution is based on the bi-encoder or poly-encoder like approach, when every cell is individually processed by the codebert, with the code/md interaction modelled with the pair of parallel TransformerDecoderLayer:

[图 1: inbox%2F743064%2Fc42b70aafb899ed52cf2ef7ed554e4f7%2Fcode_bert.png]

I either used the shared CodeBERT based encoder for both code and markdown cells or CodeBERT for code and multi language bert for markdown. The resulting activations are averaged over tokens.

The code cell activations are passed to 1D convolution with zero padding, to convert from the N code cell positions to N+1 positions between cells (bins to put mb cell to), with every point combined activations of the cell before and after.

After adding the pos encoding to the code activations (the combination of the absolute and relative encodings).

The next stage is a few layers (2 or 6) of transformer decoders, for code cell to use the self attention and attention to md cells as a memory, the same for markdown: self attention and the memory query over the output of the code cell:

for step in range(self.num_decoder_layers):
 x_code = self.code_decoders[step](x_code, x_md)
 x_md = self.md_decoders[step](x_md, x_code)

Output and loss

Outputs of the code and markdown decoders are combined with matmul similarly to attention in a transformer,

with 3 outputs:

(nb_code+1) * nb_markdown shape, is markdown cell i before the code bin j

(nb_code+1) * nb_markdown shape, is markdown cell i at the code bin j

nb_markdown * nb_markdown is the markdown cell i before another markdown cell j

[图 2: inbox%2F743064%2F863249a74f079b19943a7f6a46689e8e%2Fmodel_outputs.png]

The first two outputs are used to put the md cell to the right bin between the code cells, and the last output is used to sort md cells within the single bin. BCE loss was used during training.

Post-processing

MD cell is put to the right bin between code cells using the first prediction: probability of the MD cell i is before code bin j. The position is selected to minimize the sum of probabilities of the wrong placement over all bins:

md_cell_bin_num = np.argmin([
 -1 * md_after_code[md_idx, :i+1].sum() + md_after_code[md_idx, i+1:].sum()
 for i in range(nb_bins)
])

Such approach to select the markdown cell position worked much better compared to the simple "is markdown cell i at the code bin j" output + softmax/argmax. The intuition behind the loss and sorting approach was to have a proxy for expected number of cell swaps used in the competition metric.

The model was trained end to end, with the batch equal to a single notebook, I guess this makes the optimisation task harder due to the variable size of notebooks. Gradient clipping helped.

The loss weighting and notebooks sampling also had a significant impact on the score. Large notebooks have a larger impact on the final score (due to the large number of position inversions for wrong predictions) but the wrong prediction error is averaged over a large number of nb_md * nb_code predictions. To address this I sampled larger notebooks more often (most useful) and for some models added avg_loss + a * max_loss + b * sum_loss (with a very small a of 0.02, adding sum_loss helped for initial experiments but was disabled later).

Non-English notebooks handling

I tried to address the multiple language notebooks, I used either the same shared codebert model for code and md cells or the codebert for code and sentence-transformers/paraphrase-multilingual-mpnet-base-v2 for md.

Example of the performance difference between approaches (from the local validation, on one of folds):

shared codebert: All notebooks: 0.9113; English notebooks: 0.9164; Non-English notebooks: 0.8652

codebert+mpnet: All notebooks: 0.9088; English notebooks: 0.9117; Non-English notebooks: 0.8825

The multilingual sentence ensembling mpnet model is trained on language pairs and allows to reduce the score gap between English and non-English notebooks but it has the worse combined score (most notebooks are English).

I initially planned to do a different ensemble based on the language, but later I found the impact of ensembling codebert2 and codebert+mpnet models produces a much bigger score jump and decided to use the same large ensemble for all notebooks, regardless of the language.

Ensembling

To increase the ensemble side, I also trained the separate encoder models (using per-cell predictions from the first level transformers). Such encoder only parts of models were much faster to train (single per notebook transformer compared to multiple ber cell transformers, allowed to faster experiment with different architectures) and to predict (L1 per cell model predictions are re-used).

The ensemble - to average 3 outputs between 4 folds and two models, including two versions of L2 encoders.

For ensembling I used the simple weighted averaging of model predictions (weighting was not very important, used higher weight for better performing models but the result was almost the same as for unweighted average).

### 11th Place Solution: Nested Transformers

来源：https://www.kaggle.com/competitions/AI4Code/discussion/343680

Overview

We called our network architecture "Nested Transformers", since it contains two levels of transformers:

Cell transformer: A transformer encoder to encode cell tokens, this can be a typical transformer for NLP.

Notebook transformer: A transformer encoder with cell*cell self-attention to learn the interaction among cells.

[图 1: inbox%2F2202881%2Faad7b5931ba26287e467c535a69d595a%2Fnested_tfm.png]

Source codes: https://github.com/ShinSiangChoong/kaggle_ai4code_nested_transformers

What Worked

Modified Format of the Input to Cell Transformer

The input is in the following format: <code><sep><source_tokens> OR <mark><sep><source_tokens>

Thanks @cabbage972 for verifying the usefulness of this idea. Please refer to this comment. 

Cell Features:

The code cell order is known, while the markdown order is unknown, hence a straightforward positional embedding scheme in the notebook transformer won't work. The cell features aim to inform the model about the known code cell positions/order.

We use 2 features for each cell, i.e. cell type (code -> 1, markdown -> 0) and percentile rank among the code cells: If the cell is a markdown cell, this feature = 0

The 2 features are "expanded" by FC layers, such that they are represented as an embedding that has the same dimension with that of the cell token embeddings. 

These cell feature embeddings are then concatenated with the token embeddings and passed into the Aggregation Attention Layer together.

Aggregation Attention

We believe different tokens (and the cell features) have different importance to represent the cell. An aggregation attention layer is used to learn the weights of each token embedding (and the cell feature embedding). 

The weights are normalized by a Softmax layer, such that the final cell embedding is a weighted average of its token and feature embeddings.

Thanks @cabbage972 for verifying the usefulness of this idea. Please refer to this comment. 

Double Head Architecture

Pointwise Head: output the percentile ranks of each cell. L1 Loss is applied.

Pairwise Head: For each pair of cells A & B, predict whether cell B is the next cell of cell A. Cross-entropy loss is applied.

We only use the pointwise head for inference, i.e. the cells are ranked by the predicted percentile rank. 

The pairwise head is not used during inference, however, in our experiment, inclusion of the pairwise head helps in boosting the validation score by around 0.03.

Code Order Correction

Since our model predicts a percentile rank for each cell (including code cells), the code cell order (which is given) may be violated. 

If this happens, we swap the code cells based on the given order.

This idea only marginally boosts the score. The model actually learns the code order pretty well given the cell features.

What Didn't Work

Make use of the pairwise head prediction in a greedy manner while fulfilling the code order constraint, i.e. keep determining the next cell by selecting the cell with the highest prediction score.

Make use of the pairwise head prediction as a distance matrix, then use LKH to solve a Sequential Ordering Problem (TSP with precedence constraints)

Train 2 cell transformer backbones together end to end, rely on the Aggregation Attention to aggregate the token embeddings from the 2 backbones.

Additional Context

The final model is an ensemble of 4 different cell transformer backbones, i.e. CodeBERT, Deberta-large, Deberta-base, and DistilBERT. 

For the notebook transformer, we used 6 transformer encoder layers here, each with 8 self-attention heads. This layer "adjusts" the embedding of each cell based on the embeddings of other cells using the self-attention mechanism.
